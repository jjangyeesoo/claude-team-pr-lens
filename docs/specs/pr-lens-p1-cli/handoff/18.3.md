## 조립 팩토리의 형태
결정: `CliPipeline.review(preflight, Factories, masker, debug, out, err)`가 조립한다. `Factories(GitHubFactory github, LlmFactory llm)`는 `(token, retry, masker, debugLog)`, `(apiKey, masker, debugLog)`로 클라이언트를 만든다. `RetryingLlmClient` 감싸기와 `RetryExecutor` 생성은 조립 함수가 하고, 팩토리는 재시도 없는 클라이언트를 만든다. `Factories.real()`이 실제 구현을, 테스트는 가짜를 넘긴다.
이유: design.md "CLI 조립의 테스트 가능성"이 팩토리 인자만 정했고 시그니처는 정하지 않았다. 재시도 감싸기를 조립 쪽에 두면 가짜 클라이언트에도 같은 재시도가 적용된다.
영향받는 작업: 20.2 (아래 "골든 테스트에서 쓸 때" 참조)

## 골든 테스트에서 쓸 때
결정: `CliPipeline.review`는 항상 `PrFetcher`와 `ContextCollector`를 거친다. 출력 조립(`reportResult`, JSON 뒤 `\n`, Markdown은 그대로, stdout에 한 번 쓰기, `ExitCodeResolver`)은 이 메서드 안에만 있고 따로 떼어 쓸 수 없다. 20.2가 stdout 바이트를 `review`로 비교하려면 `GitHubFactory`에 픽스처를 돌려주는 가짜 `GitHubClient`를 넘기고, 따로 비교하려면 같은 출력 규칙을 따라야 한다.
이유: 조립을 한 메서드로 둔 결과이며 20.2 본문의 "엔진과 출력만 실행" 전제와 맞는지 확인하지 않았다.
영향받는 작업: 20.2

## redirect를 따르지 않음
결정: `CliPipeline.httpClient()`는 JDK 기본값(`Redirect.NEVER`)이고 3xx는 `HttpGitHubClient`의 기존 분류(`Attempt.Fatal`, `NonRetryableApiException`)대로 오류가 된다. tasks.md 18.3 본문의 `결정(18.3)` 줄과 같다.
이유: 따라가면 `Authorization`이 다른 호스트로 갈 수 있어 요구사항 19.6을 지키기 어렵다. 실제 GitHub의 301 응답은 확인하지 않았다.
영향받는 작업: 20.4 (이름이 바뀐 저장소의 오류 메시지가 쓸 만한지는 확인하지 않음)

## 재시도 대기와 디버그 로그
결정: 실제 `Sleeper`는 `CliPipeline.sleep`(`Thread.sleep`, 중단되면 인터럽트를 복원하고 `IllegalStateException`이라 "내부 오류가 발생했습니다 (IllegalStateException)"로 보인다)이다. `PRLENS_DEBUG`가 비어 있지 않으면 GitHub와 Claude 클라이언트의 HTTP 디버그 로그가 모두 stderr에 한 줄씩 나온다.
이유: 대기 구현이 따로 없었고, 디버그 조건을 오류 스택과 같게 맞추라는 18.5 주의를 따랐다.
영향받는 작업: 20.4 (두 경로 모두 가짜로만 확인했고 실제 API로는 확인하지 않았다)

## 확인하지 않은 하위 프로세스 사례
결정: 18.6의 하위 프로세스 확인은 환경변수 없음과 인자 없음 두 가지만 했다. 결과가 stdout에 BOM 없는 UTF-8로 나오는지, `\n` 없이 `s`로 끝나는 출력, 스트림을 닫은 뒤 `System.exit`해도 잘리지 않는지, `PRLENS_DEBUG`의 스택 출력은 확인하지 않았다.
이유: `main`이 `Factories.real()`로 고정이라 결과를 stdout에 쓰는 실행은 실제 API 없이는 만들 수 없고, 디버그 스택은 하위 프로세스에서 일으킬 방법을 찾지 못했다.
영향받는 작업: 20.4 (Windows·macOS 래퍼 실행과 함께 확인)

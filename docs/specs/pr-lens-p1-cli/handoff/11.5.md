# 11.5~11.9 메모

## ChunkOutcome과 ResultMerger.merge의 형태
결정: Chunk 하나의 결과는 package-private record `ChunkOutcome(index, files, summary, findings: List<Finding>, incompleteReason, rawResponseExcerpt, usage: Usage, failedStatus)`로 `ResultMerger.merge(List<ChunkOutcome>, List<ExcludedFile>, FileCountGap, ReviewStats)`에 넘긴다. 엔진이 `ResponseParser` → `FindingValidator` → `CostCalculator.estimate`를 마친 뒤 `Usage`(모델 이름, 비용 포함)까지 만들어 채운다. `index`는 1부터이고 단일·요약 전용 모드의 Chunk도 1이다. 재시도를 소진한 Chunk는 `ChunkOutcome.failed(index, files, lastStatus)`(usage null)로 만든다
이유: design.md는 병합 입력의 타입을 정하지 않았다. 토큰 합과 비용 합을 Chunk별 `Usage` 값으로 하면 "Chunk별로 반올림한 값의 합"(요구사항 20.10)이 그대로 된다
영향받는 작업: 12.1, 12.2

## 병합이 정한 동작
결정: 실패한 Chunk(usage null)는 토큰 0, 비용 0으로 더하고 summary에서 뺀다(머리줄의 `n/N`은 실패 Chunk를 센 전체 Chunk 수와 원래 번호). 파일이 여럿인 Chunk의 머리줄은 경로를 `, `로 잇는다. `FILES_TRUNCATED`는 Chunk 사유 뒤에 둔다. `merge`는 `outcomes`가 비었거나 `usage`가 있는 Chunk가 하나도 없으면 `IllegalArgumentException`이다
이유: 요구사항이 정하지 않은 부분이다. 모든 Chunk 실패는 `merge` 전에 엔진이 `AllChunksFailedException`으로 처리해야 한다
영향받는 작업: 12.1

## PromptBuilder 사용법
결정: `PromptBuilder.build(mode, chunk, snapshot, context, config)`는 모드와 무관하게 SINGLE은 대상 전체(원래 순서)를 `chunk`로, SPLIT은 `ChunkPlanner.plan`의 Chunk를 넘긴다. `system`과 첫 user 블록은 `mode`, `chunk`, PR 텍스트를 읽지 않으므로 Chunk마다 같은 바이트다. `Revision.HEAD` 컨텍스트 파일은 둘째 블록의 `<prlens:head_spec>` 하나에 모두 모인다. 요약 전용 모드의 `findings` 강제 빈 목록은 엔진 몫이다(프롬프트는 모델에 그렇게 답하라고만 한다)
이유: 요구사항 14.6, 20.6, 20.7. 엔진이 Chunk 목록과 모드를 이미 알고 있다
영향받는 작업: 12.1, 12.2(Property 34)

## 비용 단가 조회
결정: `CostCalculator.estimate(LlmUsage, ModelPricing)`는 단가가 null이면 null을 돌려준다. 엔진이 `config.pricing().get(config.model())`을 넘긴다(맵에 없으면 null이 그대로 간다)
이유: 요구사항 20.5
영향받는 작업: 12.1

## 이름 변경 파일의 이전 경로는 프롬프트에 없다
결정: 11.5는 `ChangedFile.previousPath()`를 모델에 보여 주지 않는다. 이 작업에서 미룬다
이유: 요구사항에 없다. 필요하면 데이터 영역의 `file_diff` 앞에 머리줄을 더하는 별도 결정이 필요하다
영향받는 작업: 없음(필요해지면 11.5의 `PromptBuilder`를 고친다)

## NO_TARGET과 FILES_TRUNCATED는 merge 밖에서 다룬다
결정: 대상 0개(`NO_TARGET`)는 `ResultMerger`를 쓰지 않고 엔진이 `ReviewResult`를 직접 만든다(`files_truncated` 사유와 `FileCountGap`도 직접 넣는다). `merge`는 `fileCountGap`이 null이 아닐 때 `FILES_TRUNCATED`를 Chunk 사유 뒤에 스스로 더하므로, 엔진은 이 사유를 `ChunkOutcome.incompleteReason`에 넣지 않는다(넣으면 `ChunkIssue`로 잘못 기록된다)
이유: Chunk가 없으면 `merge` 입력(usage가 있는 Chunk)을 만들 수 없다
영향받는 작업: 12.1

## 마지막 상태 코드는 숫자일 때만 Integer로 넘긴다
결정: `RetriesExhaustedException.lastStatus()`는 "마지막 상태 코드 또는 네트워크 오류 종류"를 담은 `String`이고 `ChunkOutcome.failed`와 `ChunkIssue.lastStatusCode`는 `Integer`다. 숫자가 아니면(네트워크 오류) null로 넘기고 `Integer.parseInt`를 그대로 쓰지 않는다
이유: 그대로 파싱하면 네트워크 오류에서 `NumberFormatException`이 난다
영향받는 작업: 12.1

## 프롬프트 검사의 표식 생성기
결정: system 프롬프트에는 `<prlens:team_context>`, `<prlens:file_diff>` 같은 태그 이름과 `security`, `summary`, `findings` 같은 단어가 원문으로 들어 있다. Property 34의 고유 표식은 이 문구의 부분 문자열이 될 수 없는 값(고정 접두어와 UUID)으로 만들고, 태그 개수는 요청 전체가 아니라 블록별로 센다
이유: 표식이 system 문구와 겹치면 "system에 표식이 없다" 검사가 오탐한다
영향받는 작업: 12.2

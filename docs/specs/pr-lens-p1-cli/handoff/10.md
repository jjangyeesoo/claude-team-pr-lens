# 작업 10 메모 (브랜치 feat/t1-p1-10-response-validation)

## ResponseParser의 결과 타입 `ParsedResponse`
결정: `review` 패키지의 package-private record `ParsedResponse(summary, findings: List<RawFinding>, incompleteReason: IncompleteReason|null, rawResponseExcerpt: String|null, usage: LlmUsage)`를 돌려준다. `incompleteReason == null`이면 complete이고, `schema_violation`일 때만 `rawResponseExcerpt`(원본 앞 2,000자)가 있다. `RawFinding(file, line, severity, category, message, suggestion, basisType, basisRef)`는 라인 판정 전의 값이다.
이유: design.md는 비공개 `RawFinding`만 정하고 파서의 반환 타입은 정하지 않았다. 엔진이 `IncompleteReason`과 발췌문을 `ChunkIssue`로 옮기려면 한 값으로 받는 편이 단순하다.
영향받는 작업: 10.4(입력이 `RawFinding`), 11.8(`ChunkIssue.rawResponseExcerpt`에 이 발췌문을 쓴다), 12.1(Chunk마다 `parse` 결과를 받아 검증·비용·병합으로 넘긴다)

## usage 변환은 엔진 몫
결정: 파서는 `LlmUsage`를 그대로 싣고, 모델 이름과 비용이 들어가는 `Usage`로의 변환은 하지 않는다.
이유: 모델 이름과 단가는 `Configuration`에 있고 파서는 설정을 받지 않는다.
영향받는 작업: 11.6, 12.1 (`CostCalculator.estimate(LlmUsage, ModelPricing)`의 입력으로 `ParsedResponse.usage()`를 쓴다)

## 라인 판정(10.4, 10.5)은 이 PR에서 미룸
결정: 10.4 `FindingValidator`와 10.5(Property 23~26)는 이 브랜치에서 하지 않았다. 5.3 `LineRanges`가 스텁이라 라인 판정 테스트를 쓸 수 없기 때문이다.
이유: 설계는 `head 경로 → LineRanges` 맵을 입력으로 한다. 5.3 머지 뒤에 이어서 한다.
영향받는 작업: 10.4, 10.5, 12.1 (10.4에 "주의(선머지 리뷰)"의 `Basis.ref` null 검사 순서가 그대로 남아 있다)

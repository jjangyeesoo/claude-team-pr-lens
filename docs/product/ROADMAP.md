# ROADMAP: PR Lens 5주 계획

- 작성일: 2026-09-30 · 관련 문서: [PRD](PRD.md) · [진행 방식(플레이북)](PLAYBOOK.md)
- 원칙: **전원이 매주 구현하고, 역할(모자)은 그 주에 추가로 맡는 책임이다.** 역할별 책임은 [플레이북 2장](PLAYBOOK.md#2-역할모자-정의)을 따릅니다.
- 스타터: [`claude-team-starter`](../../README.md)의 `main` 브랜치(풀스택 버전, `backend/` + `web/`)를 씁니다.
- **주차별 일정은 가이드이고 강제하지 않습니다 (2026-10-04 결정).** 스펙을 정리해 보니 P1을 2주차, P2를 3주차, P3를 4주차에 끝내는 것은 무리였습니다. 2~4주차 3주 동안 P1 → P2 → P3 순서로 되는 데까지 개발하고, 5주차에 그동안의 경험을 정리해 발표합니다. 고정된 것은 개발 기간(2~4주차), 4주차 금요일 기능 동결, 5주차 발표입니다. 아래 주차별 마일스톤과 완료 조건은 목표이고, 단계가 그 주에 끝나지 않으면 다음 주에 이어서 합니다([일정 운영](#일정-운영)).

## 한눈에 보기

| 주차 | 마일스톤 | 기능 리드 | 컨텍스트 담당 | 리뷰어 | 방법론 실험 포인트 |
|---|---|---|---|---|---|
| 1 | M0 기반과 합의 | 전원 (진행 B) | 전원 (회고 A) | 전원 | CLAUDE.md 공동 작성, 지표 기준선 |
| 2 | M1 CLI MVP | **B** | **A** | **C** | 스펙 주도 개발, 첫 역할 순환 |
| 3 | M2 자동화·저장 | **A** | **C** | **B** | 도그푸딩 시작, 사람 리뷰 vs 도구 리뷰 |
| 4 | M3 웹 조회 | **C** | **B** | **A** | 두 번째 스택(FE) 규칙 분리 |
| 5 | 안정화·발표 | 전원 (진행 C) | 전원 (회고 B) | 전원 | 지표 정리, 회고 |

- 1주차와 5주차는 역할이 없는 대신 **진행자**와 **회고 작성자**를 둡니다(괄호 안). 진행자는 그 주의 기능 리드 역할(킥오프, 중간 점검, 범위 조정)을 맡습니다. 1주차 진행자는 2주차 기능 리드 B, 1주차 회고 작성자는 2주차 컨텍스트 담당 A입니다(다음 주로 바로 이어지도록). 승인 규칙은 [플레이북 2장](PLAYBOOK.md#승인-규칙-요약)의 "1·5주차" 행을 따릅니다.
- 주차별 작업은 3개 트랙(T1~T3)으로 나눕니다. **같은 모듈을 두 트랙이 동시에 건드리지 않도록** 나누고, 여러 트랙이 함께 쓰는 파일(인터페이스 타입, 공용 레이아웃 등)은 월요일에 기능 리드가 먼저 머지합니다([가이드 5.4](../guide/claude-code-team-methodology.md#54-브랜치와-pr-전략)). 트랙 배정은 월요일 킥오프에서 기능 리드가 확정하고, 아래 배정은 기본안입니다.
- **다음 주 스펙은 목요일까지 초안**을 쓰고, 금요일 회고 전에 승인합니다(2·3주차). 스펙 승인 규칙은 플레이북을 따릅니다.

## 1주차: M0 기반과 합의 (전원)

**목표**: 2주차 월요일에 세 사람이 바로 병렬로 구현을 시작할 수 있는 상태.

- [ ] (전원, 진행 B) PRD 검토와 확정 (상태 `approved`), 제품 이름, 1인당 주당 투입 시간 합의
- [ ] (A) 저장소 생성: 스타터를 복사하고 패키지 이름(`com.example.starter`)과 프로젝트 이름을 PR Lens로 바꾸기. 메모 샘플 도메인은 참고 예시로 두었다가 2주차 첫 기능 PR에서 지운다
- [ ] (A) CLAUDE.md 다듬기 (200줄 미만, 브랜치 규칙을 [플레이북 6장](PLAYBOOK.md#6-작업-규칙) 형식으로 수정), `.claude/settings.json`과 hooks 동작 확인 (전원 `/context`, `/hooks` 확인)
- [ ] ADR 4건 작성과 승인 ([PRD 10장](PRD.md#10-결정이-필요한-것-1주차)): 0007 저장소 구조(A, 번호 0003은 패키지 구조 결정에 썼음), 0004 CLI 라이브러리(C), 0005 LLM 설정(B), 0006 DB·테스트(B)
- [ ] 기술 검증(spike), 결과는 `docs/spikes/`에 짧게 기록
  - (A) GitHub API로 실제 PR의 diff 가져오기
  - (B) Claude API 구조화된 출력으로 리뷰 JSON 한 번 받기, 토큰과 비용 실측
  - (C) smee.io로 로컬에서 webhook 이벤트 받기
- [ ] 2주차 스펙 검토와 승인 (세 트랙을 스펙 하나 [`pr-lens-p1-cli`](../specs/pr-lens-p1-cli/README.md)로 묶어 작성함. 각자 자기 트랙의 요구사항, 설계, 작업을 검토: T1 B, T2 A, T3 C)
- [ ] (C) 지표 기록 방식 합의와 기준선 기록 ([플레이북 5장](PLAYBOOK.md#5-지표-기록)), PR 템플릿의 `AI 리뷰 지적 n건 / 반영 m건` 칸 확인
- [ ] (C) GitHub 저장소 설정: 브랜치 보호(승인 1건 필수, CI 필수 체크 `backend`·`web`), 라벨(`context`, `track-1`, `track-2`, `track-3`)
  - 주의: GitHub 무료 플랜에서는 **비공개 저장소에 브랜치 보호와 ruleset을 쓸 수 없습니다**(API 403). 공개 저장소로 만들거나, GitHub 조직(Team 플랜)이나 Pro 계정에 만들거나, 보호 없이 [플레이북](PLAYBOOK.md#승인-규칙-요약)의 사람 규칙으로 운영할지 1주차에 정합니다
  - 공개로 만든다면 커밋 이메일이 공개됩니다. 전원이 GitHub의 noreply 주소(`<id>+<login>@users.noreply.github.com`)를 저장소 `user.email`로 설정하고 첫 커밋을 합니다
- [ ] (A, 금요일) 1주차 회고 노트 `docs/retro/week-1.md`

**완료 조건**: backend `./gradlew test`와 web `npm run verify` 통과(CI green), 2주차 스펙(`pr-lens-p1-cli`) `approved`, ADR 4건 머지.

## 2주차: M1 CLI MVP (리드 B · 컨텍스트 A · 리뷰어 C)

**목표**: `prlens review <PR URL>`로 팀 컨텍스트를 반영한 리뷰를 터미널에서 본다. (FR-1~6)

| 트랙 | 담당 | 작업 | 관련 FR |
|---|---|---|---|
| T1 | B (리드) | 리뷰 엔진: 프롬프트 구성, Claude API 호출, 결과 파싱과 `basis` 검증, 대형 PR 분할 | FR-4, FR-6 |
| T2 | A | GitHub 연동: PR·diff 조회, 파일 필터링, 팀 컨텍스트 수집(rules `paths` 매칭, 스펙 링크) | FR-1~3 |
| T3 | C | CLI 명령과 출력(Markdown/JSON, 종료 코드), 테스트 픽스처(실제 PR diff 샘플 3~5개) | FR-5 |

- **인터페이스 먼저**: 월요일에 T1~T3 사이 인터페이스(`PullRequestSnapshot`, `ReviewContext`, `ReviewResult`)를 리드가 정의해 먼저 머지합니다. 이후 트랙은 이 타입만 보고 병렬로 진행합니다.
- **컨텍스트 담당 A의 추가 작업**: 모듈별 rules 파일 정리(`backend/github`, `backend/review`), 첫 주에 반복된 실수를 규칙으로 흡수.
- **완료 조건 (금요일 데모)**: 팀 저장소의 실제 PR 1건을 CLI로 리뷰하고, 규칙 근거가 붙은 지적이 1건 이상 나온다.

## 3주차: M2 자동화·저장 (리드 A · 컨텍스트 C · 리뷰어 B)

**목표**: PR이 열리면 자동으로 리뷰가 PR에 달리고, 결과가 DB에 쌓인다. (FR-7~11) **이번 주부터 팀 PR 전부에 PR Lens 리뷰를 시도합니다(도그푸딩, 목표 80%).** 자동 게시가 완성되기 전에는 CLI 결과를 PR 설명에 붙입니다.

| 트랙 | 담당 | 작업 | 관련 FR |
|---|---|---|---|
| T1 | A (리드) | webhook 수신(서명 검증), 비동기 실행, head SHA 기준 중복 방지 | FR-7, FR-8 |
| T2 | B | DB 스키마와 저장(`repository`, `pull_request`, `review_run`, `finding`), 조회 REST API 초안(OpenAPI) | FR-9, FR-12 일부 |
| T3 | C | GitHub 게시(요약 코멘트 갱신, 라인 코멘트), 채택/기각 수집 | FR-10, FR-11 |

- **패키지 경계 먼저**: T1과 T3가 모두 GitHub 연동을 쓰므로, 월요일 킥오프에서 패키지 경계(예: `webhook/` 수신, `github/` API 클라이언트, `store/` 저장)와 T2의 저장 인터페이스를 리드가 먼저 머지합니다. FR-8 중복 방지는 이 인터페이스를 사용합니다.
- **리뷰어 B의 추가 작업**: 팀 PR마다 "사람 리뷰 지적"과 "PR Lens 지적"을 비교해 기록(겹침, 도구만 찾음, 사람만 찾음). 5주차 발표의 핵심 데이터입니다.
- **컨텍스트 담당 C의 추가 작업**: 4주차에 대비해 스타터의 `web/` rules와 `web/CLAUDE.md`가 PR Lens 화면에 맞는지 검토, CLAUDE.md 가지치기.
- **완료 조건**: 새 PR을 열면 2분 안에 요약 코멘트가 달리고, 커밋을 추가하면 요약 코멘트가 갱신된다. "2분"은 P2 요구사항 17.1의 방식으로 잽니다(서버가 webhook을 받은 시각부터 게시 완료까지, 재시도 대기 시간과 smee 전달 지연 제외).

## 4주차: M3 웹 조회 (리드 C · 컨텍스트 B · 리뷰어 A)

**목표**: 웹에서 PR별 리뷰 이력과 규칙 위반 통계를 본다. (FR-12~14)

| 트랙 | 담당 | 작업 | 관련 FR |
|---|---|---|---|
| T1 | C (리드) | 메모 샘플 화면 제거, PR Lens 화면 골격(레이아웃·내비게이션), PR 목록·상세 화면 | FR-13 |
| T2 | A | 조회 API 보강(페이지네이션, 에러 포맷), 통계 집계 API, 그에 맞춘 `web/src/lib/api/types.ts` | FR-12, FR-14 |
| T3 | B | 통계 화면(규칙별 지적, 심각도 분포, 채택률, 비용 추이) | FR-14 |

- **공용 파일 먼저**: 월요일에 리드 C가 화면 골격(레이아웃, 내비게이션, 라우트 폴더)을, A가 `types.ts`의 타입 정의를 먼저 머지합니다. 이후 **API PR만 `types.ts`를 수정하고 화면 PR은 수정하지 않습니다**(스타터 규칙 "API가 바뀌면 DTO와 types.ts를 같은 PR에서"를 이 프로젝트에 적용한 방식).
- web은 Server Component에서 backend를 호출하므로 CORS 설정은 필요 없습니다.

- **컨텍스트 담당 B의 추가 작업**: 스타터에 있는 `web/CLAUDE.md`(하위 디렉터리 지시문)와 `.claude/rules/frontend/`를 PR Lens 화면에 맞게 고치고, FE 작업 세션에서 BE 규칙이 로드되지 않는지 `/context`로 확인. 스택이 둘일 때 컨텍스트를 나누는 방법이 이번 주의 실험입니다.
- **금요일 = 기능 동결.** 어느 단계까지 왔든 이날 개발을 멈추고, 이후에는 버그 수정만 합니다.
- **완료 조건**: 로컬에서 BE와 web을 띄워 3주차부터 쌓인 실제 리뷰 데이터를 화면으로 본다.

## 5주차: 안정화와 발표 (전원)

| 요일 | 할 일 |
|---|---|
| 월~화 | 버그 수정, 데모 시나리오 고정, 지표 집계 |
| 수 | 최종 회고 (3주간 역할별 소감, 무엇이 효과 있었나) |
| 목 | 발표 자료 완성과 리허설 |
| 금 | **성과 발표** |

**발표 구성 (안)**
1. 문제와 제품 소개 (5분): 팀 컨텍스트 기반 리뷰란
2. 데모 (10분): CLI → PR 자동 코멘트 → 웹 통계 중 기능 동결 때까지 완성한 단계. 못 한 단계는 어디까지 했고 왜 못 했는지를 말합니다
3. 방법론 적용 결과 (15분)
   - 지표: PR 리드타임, 리뷰 반려율, 같은 지적 반복 횟수와 규칙 흡수율, AI 리뷰 채택률, PR당 비용
   - 사람 리뷰 vs PR Lens 리뷰 비교 (3주차부터 기록한 데이터)
   - 역할 순환 회고: 각 역할에서 배운 것, 인수인계에서 잃은 것
4. 가이드에 반영할 개선점 (5분): [방법론 가이드](../guide/claude-code-team-methodology.md)에 PR로 올릴 항목

---

## 일정 운영

- 단계(P1, P2, P3)가 목표 주차에 끝나지 않으면 **다음 주에 이어서 합니다.** 다음 단계는 앞 단계의 데모 최소 경로(각 스펙 `tasks.md`의 Notes)가 끝난 뒤에 시작합니다.
- 역할(기능 리드, 컨텍스트 담당, 리뷰어)은 단계와 상관없이 **주 단위로 그대로 순환합니다.** 그 주의 기능 리드가 진행 중인 단계를 이어받고, 트랙 담당은 각 스펙의 배정을 따릅니다. 넘어온 작업은 금요일 회고 노트의 인수인계에 적습니다.
- 수요일 중간 점검에서 그 주에 끝낼 것과 다음 주로 넘길 것을 정하고, 이 문서의 "진행 상황"을 고칩니다.
- 4주차 금요일에 개발을 멈춥니다. 그때까지 못 한 단계는 발표에서 "못 한 것과 이유"로 다룹니다. 이 프로젝트의 결과물은 제품 완성도보다 방법론을 적용한 경험입니다.

## 일정 위험과 완충

- 단계 안에서 범위를 줄여야 할 때의 순서: FR-14 통계 → FR-11 채택/기각 자동 수집 → FR-6 대형 PR 분할. FR-11을 줄여도 채택률 지표는 PR 설명의 수기 기록으로 계속 모읍니다(발표의 핵심 데이터이므로).
- 3주차 webhook이 막히면 GitHub Actions에서 CLI를 실행해 코멘트를 게시하는 방식으로 대체합니다(FR-7, FR-8 연기). 이 경로에서는 호스팅 러너가 로컬 DB에 닿지 않아 저장(FR-9), 채택/기각 수집(FR-11), 조회 API의 데이터도 함께 비게 됩니다. 결과를 남기는 방법은 P2 요구사항의 결정 대기 D-15에서 정합니다.

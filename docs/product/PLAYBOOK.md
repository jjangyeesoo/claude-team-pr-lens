# 연구회 진행 방식 (플레이북)

- 작성일: 2026-09-30 · 관련 문서: [PRD](PRD.md) · [ROADMAP](ROADMAP.md)
- 이 문서는 [팀 방법론 가이드](../guide/claude-code-team-methodology.md)를 3명이 5주 동안 실제로 적용하는 규칙입니다. 일반 원칙은 [가이드 5.5 역할 순환 운영](../guide/claude-code-team-methodology.md#55-역할-순환-운영-겸직-모델)에 있고, 여기에는 이 연구회만의 구체적인 운영 방식을 적습니다.

---

## 1. 기본 원칙

1. **전원이 매주 구현한다.** 역할은 본업이 아니라 그 주에 추가로 쓰는 "모자"입니다.
2. **역할은 주 단위로 순환한다.** 3명이 3주 동안 세 역할을 한 번씩 맡습니다.
3. **AI가 쓴 코드도 작성자 책임이다.** PR 작성자는 모든 변경 줄을 설명할 수 있어야 합니다.
4. **인수인계는 대화 기록이 아니라 문서로 한다.** 스펙, PR 설명, 주간 회고 노트가 유일한 인수인계 수단입니다.

| 주차 | A | B | C |
|---|---|---|---|
| 2 | 컨텍스트 담당 | **기능 리드** | 리뷰어 |
| 3 | **기능 리드** | 리뷰어 | 컨텍스트 담당 |
| 4 | 리뷰어 | 컨텍스트 담당 | **기능 리드** |

## 2. 역할(모자) 정의

역할 업무에는 **주당 투입 시간의 20~30%**(전일 근무라면 하루 1~2시간)를 쓰고, 나머지는 자기 트랙 구현에 씁니다. 투입 시간은 1주차에 합의합니다([PRD](PRD.md) 헤더).

### 기능 리드

그 주 마일스톤의 결과를 책임집니다.

- 월요일 킥오프 진행: 트랙 배정 확정, 트랙 사이 인터페이스를 먼저 정의해 머지
- 스펙 3건이 `approved` 상태인지 확인 (없으면 월요일 오전에 함께 작성)
- 수요일 중간 점검에서 범위 조정 (밀리면 줄일 것을 결정)
- 트랙 통합과 금요일 데모
- 리뷰어가 올린 PR의 승인자 (리뷰어는 자기 PR을 승인할 수 없으므로)

### 컨텍스트 담당

팀의 AI 컨텍스트(`CLAUDE.md`, `.claude/`, `docs/adr/`)를 관리합니다. [가이드 2.2](../guide/claude-code-team-methodology.md#22-claudemd-설계-무엇을-넣고-무엇을-뺄까)의 운영 규칙을 이번 주에 책임지는 사람입니다.

- `context` 라벨이 붙은 PR(`.claude/`, `CLAUDE.md` 변경)의 **필수 승인자**
- "실수 → 규칙" 루프 운영: 팀원이 "Claude가 또 이걸 틀렸다"고 알리면 규칙 PR로 만든다. 반대로 없어도 되는 규칙은 지운다
- 주 1회 가지치기: CLAUDE.md 200줄 미만 유지, `/context`로 로드 상태와 용량 확인
- 금요일 회고 진행과 [회고 노트](#4-주간-회고와-인수인계) 작성
- (이 프로젝트 한정) PR Lens의 리뷰 프롬프트도 "컨텍스트"로 보고 변경을 관리

### 리뷰어

사람 리뷰의 최종 책임자입니다.

- 자기 PR과 `context` PR을 뺀 모든 PR의 **기본 승인자** (영업일 기준 24시간 안에 첫 리뷰)
- AI 리뷰 결과(reviewer 서브에이전트, 3주차부터는 PR Lens) 중 무엇을 반영할지 판단하고, 기각한 이유를 PR에 남긴다
- [가이드 4.1](../guide/claude-code-team-methodology.md#41-ai-생성-코드-리뷰-기준-팀-pr-체크리스트)의 "사람이 특히 볼 것"(그럴듯하지만 틀린 코드, 과잉 설계, 테스트 약화, 의존성 추가) 확인
- 같은 지적이 두 번 나오면 컨텍스트 담당에게 규칙화를 요청
- 작성자가 PR 설명에 적은 `AI 리뷰 지적 n건 / 반영 m건`이 맞는지 확인하고, 틀리면 고친다 ([5장](#5-지표-기록))

### 승인 규칙 요약

| PR 종류 | 필요한 승인 |
|---|---|
| 일반 기능 PR | 리뷰어 1명 |
| 리뷰어가 작성한 PR | 기능 리드 1명 |
| `.claude/`, `CLAUDE.md` 변경 (`context` 라벨) | 컨텍스트 담당 1명으로 충분 (작성자가 컨텍스트 담당이면 리뷰어) |
| 스펙 (`docs/specs/`) | 그 주(또는 다음 주) 기능 리드 1명. 작성자가 기능 리드면 다른 1명 |
| ADR, PRD 변경 | 작성자를 뺀 2명 모두 |
| 의존성 추가 | 리뷰어 + 이유 설명 (작성자가 리뷰어면 기능 리드) |
| **1·5주차** (역할 없음) 모든 PR | 작성자를 뺀 1명. ADR·PRD는 작성자를 뺀 2명 |

- GitHub 브랜치 보호의 "승인 1건 필수"는 **누가** 승인했는지까지는 강제하지 못합니다. 위 표는 사람이 지키는 규칙이고, 리뷰어가 머지 전에 확인합니다. 강제하고 싶다면 매주 월요일 `CODEOWNERS`를 그 주 역할에 맞게 바꾸는 PR을 올리고 "Code Owner 승인 필수"를 켭니다.

## 3. 주간 리듬

| 언제 | 무엇 | 시간 | 진행 |
|---|---|---|---|
| 월 오전 | 킥오프: 지난주 인수인계 노트 읽기, 트랙 배정, 인터페이스 합의 | 30분 | 기능 리드 |
| 매일 | 비동기 공유: 어제 한 것, 오늘 할 것, 막힌 것 (팀 채널에 3줄, 채널은 1주차에 지정) | - | 각자 |
| 수 | 중간 점검: 완료 조건 대비 진행, 범위 조정 | 15분 | 기능 리드 |
| 금 | 데모와 회고, 다음 주 역할 인수인계 | 45분 | 데모: 기능 리드 · 회고: 컨텍스트 담당 |

## 4. 주간 회고와 인수인계

금요일에 컨텍스트 담당이 `docs/retro/week-N.md`를 작성합니다. 역할이 없는 1·5주차는 [ROADMAP](ROADMAP.md#한눈에-보기)에 정한 회고 작성자가 씁니다. **다음 주에 같은 역할을 맡는 사람이 이 노트만 읽고 시작할 수 있어야 합니다.**

```markdown
# N주차 회고 (기능 리드: X · 컨텍스트: Y · 리뷰어: Z)

## 결과
- 마일스톤 완료 여부, 못 한 것과 이유

## 지표 (이번 주)
- PR 수 / 평균 리드타임 / 반려율
- AI 리뷰 지적 수 / 채택 수
- 규칙 추가·삭제 수 (링크)

## 역할별 인수인계
- 기능 리드 → 다음 기능 리드: 열려 있는 이슈, 기술 부채
- 컨텍스트 담당 → 다음 담당: 규칙화 대기 중인 반복 실수, 고민 중인 규칙
- 리뷰어 → 다음 리뷰어: 자주 본 문제 유형, 리뷰 대기 PR

## 방법론 관찰 (발표 재료)
- 효과 있었던 것 / 없었던 것 / 가이드에 반영할 것
```

## 5. 지표 기록

가볍게 기록하는 것이 목표입니다. 대부분은 PR과 GitHub에서 자동으로 뽑습니다.

| 지표 | 출처 | 기록 방법 |
|---|---|---|
| PR 리드타임, 반려율 | GitHub | 금요일에 `gh pr list --state all --limit 500 --json number,state,createdAt,mergedAt,closedAt,reviews`로 집계 (`gh pr list`는 기본 30건만 돌려줌). **리드타임** = 생성부터 머지까지. **반려율** = `CHANGES_REQUESTED` 리뷰를 한 번 이상 받은 PR의 비율 |
| AI 리뷰 지적 수, 채택 수 | PR 설명 | PR 템플릿의 `AI 리뷰 지적 n건 / 반영 m건` 칸에 작성자가 기록, 리뷰어가 확인. 3주차부터 FR-11 자동 수집과 병행 |
| 같은 지적 반복 → 규칙 흡수 | `context` 라벨 PR | 규칙 PR 설명에 "어떤 PR에서 몇 번 나왔는지" 링크 |
| 사람 vs PR Lens 비교 (3주차~) | 리뷰어 기록 | `docs/metrics/review-compare.md`에 PR별로 겹침/도구만/사람만 개수 |
| API 비용 | PR Lens 실행 결과 `usage` | 3주차부터 DB에서 집계 |
| 주관 만족도 | 회고 | 금요일에 역할별 5점 척도 |

**1주차 기준선**: 2주차 이전에 작업한 PR(1주차 설정 PR 등)로 리드타임을 한 번 측정해 둡니다. 기준선이 없으면 5주차에 비교할 대상이 없습니다.

## 6. 작업 규칙

[가이드 3장](../guide/claude-code-team-methodology.md#3-개발-프로세스)과 [5장](../guide/claude-code-team-methodology.md#5-역할-분담병렬-작업)을 따르되, 이 연구회에서 정한 값은 다음과 같습니다.

- **상위 작업 하나 = 브랜치 하나 = PR 하나.** 스펙이 작업 목록(`tasks.md`)을 가진 경우, 상위 작업 하나를 PR 하나로 냅니다. 작업 목록에 "PR 경계"가 표시된 작업은 그 경계대로 나눕니다. 구현과 그 테스트는 같은 PR에 넣습니다. 작업 목록이 없는 작은 스펙은 스펙 하나가 PR 하나입니다. 한 문장으로 설명되는 변경은 스펙 없이 진행
- **크기 목표는 `src/main` 변경 400줄 이하**(테스트, 픽스처, 문서는 세지 않음). 넘으면 PR 설명에 이유를 적습니다
- 브랜치: `feat/<track>-<slug>` (예: `feat/t2-diff-filter`), `fix/<track>-<slug>`. 트랙과 무관한 변경은 `docs/<slug>`, `chore/<slug>`. 커밋: Conventional Commits. 루트 `CLAUDE.md`도 같은 형식입니다
- 병렬 세션은 `claude --worktree <이름>`으로 분리. 이 명령은 `worktree-<이름>` 브랜치를 만드므로, worktree 안에서 `git branch -m feat/<track>-<slug>`로 이름을 바꾼 뒤 push합니다
- PR 전에 `/pr-ready` 실행, 검증 증거(테스트 명령과 결과)를 PR에 첨부
- 구현 세션과 리뷰 세션은 분리 ([가이드 5.3](../guide/claude-code-team-methodology.md#53-작성자와-리뷰어-세션-분리))
- 리뷰 대상은 연구회 저장소와 공개 저장소만. 회사 코드를 외부 LLM에 보내지 않음
- API 키는 각자 `.env`나 환경변수로 두고 커밋하지 않음 (deny 규칙과 hook으로 강제)

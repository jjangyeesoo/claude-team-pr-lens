# 0005. LLM 설정: 모델·effort·최대 출력 토큰·캐시 지점·refusal fallback
- 상태: accepted · 날짜: 2026-10-08

## 배경
PR Lens는 리뷰마다 Claude API를 호출한다. PRD 6장은 기본 모델을 `claude-opus-5-5`로 두고 effort와 비용은 "1주차 기술 검증에서 실측"한 뒤 ADR로 정하기로 했다(PRD 10장, P1 요구사항의 결정 대기 D-2, 설계의 G-5). P1 스펙은 제안값(`medium`, 최대 출력 토큰 16,000, fallback 미사용)으로 쓰여 있다.

이 결정이 필요한 이유는 셋이다.

- 이 모델은 thinking을 끌 수 없고 thinking 토큰도 출력으로 과금된다. effort에 따라 비용과 응답 시간이 얼마나 달라지는지 알아야 1회 리뷰 비용 상한 $0.50(요구사항 18.4)과 응답 시간 예산(P1 120초, P2의 Claude 호출 90초)을 지킬 수 있는지 판단한다.
- 이 모델의 effort 기본값은 `medium`으로 이전 모델(`high`)과 다르다. 요청에 명시하지 않으면 모델을 바꿀 때 조용히 달라진다.
- 스펙 검토(2026-10-04)에서 외부 제약 넷이 이 ADR로 넘어왔다(P1 설계 "ADR-0005에서 함께 정할 것"): spend limit 429의 재시도, 비스트리밍 제한 시간과 최대 출력 토큰 상한의 충돌, refusal 시 서버 측 fallback, 단일 모드의 캐시 지점.

확인한 사실(`docs/spikes/2026-10-08-llm-settings.md`, 300줄대 PR 두 건과 보안 수정 diff 한 건, 호출 15회, 한 사람이 한 번씩 실행한 값):

- 비용은 1회 $0.06~$0.16이고 대부분 입력이다. effort를 `low`에서 `high`로 올려도 차이는 약 $0.04다.
- 응답 시간은 `low` 10~15초, `medium` 18~29초, `high` 27~33초다.
- 출력 토큰은 최대 3,374였다. thinking 토큰은 `low` 0, `medium` 약 500, `high` 약 2,000이다. 관측한 출력 속도는 초당 약 110 토큰이다.
- 출력이 `max_tokens`에 닿으면 HTTP 200에 `stop_reason`이 `max_tokens`로 오고 본문 JSON이 중간에 끊긴다. thinking 토큰도 한도에 포함된다.
- 캐시는 JSON 스키마의 키 순서가 요청마다 같아야 읽힌다. 순서를 고정한 뒤에는 PR이 달라도, effort가 달라도 같은 팀 컨텍스트 캐시를 읽었다. 캐시 쓰기의 추가 비용은 약 $0.007, 읽었을 때의 절감은 약 $0.026이다.
- 공격 문자열이 든 보안 수정 diff에서 refusal은 나오지 않았다. `fallbacks: "default"` 요청은 Java SDK에서 받아들여졌지만, refusal이 없어 대체 모델로 넘어가는 동작은 보지 못했다.

## 결정
- **모델**: 기본값은 `claude-opus-5-5`다. 설정 파일로 바꿀 수 있다.
- **effort**: 기본값은 `medium`이다. 설정값이 기본값과 같아도 요청의 `output_config.effort`에 항상 명시한다.
- **최대 출력 토큰**: 기본값은 16,000, 설정으로 줄 수 있는 범위는 1~20,000이다. 상한을 128,000에서 20,000으로 낮춘다. 비스트리밍 요청의 제한 시간 180초 안에 받을 수 있는 양에 맞춘 값이다.
- **캐시 지점**: 단일 모드와 분할 모드 모두 팀 컨텍스트 블록 끝에 둔다(요구사항 20.6 유지). 구조화된 출력의 JSON 스키마는 직렬화 결과가 실행마다 같도록 순서가 고정된 형태로 둔다.
- **refusal fallback**: P1에서는 쓰지 않는다. `stop_reason`이 `refusal`이면 지금 설계대로 불완전 결과(사유 `refusal`, 종료 코드 3)로 끝낸다.
- **spend limit 429**: 지금의 재시도 규칙(최대 3회)을 그대로 둔다. 일반 429와 구분하는 방법을 확인하면 재시도 없이 끝내도록 바꾼다.
- **1회 리뷰 비용 상한과 단가**: 요구사항 18.4의 값($0.50, 입력 $4.00, 출력 $20.00, 캐시 쓰기 $5.00, 캐시 읽기 $0.20)을 그대로 둔다.

## 고려한 대안
- **effort 기본값 `high`**: 더 깊이 검토할 여지가 있고 비용 차이가 $0.01~$0.03으로 작다. 하지만 응답이 10초쯤 느려지고, 늘어난 출력은 거의 thinking이며, 이 표본에서 지적 수와 내용은 `medium`과 비슷했다. 품질이 낫다는 근거가 생기면 설정 기본값만 바꾸면 된다.
- **effort 기본값 `low`**: 가장 싸고 빠르다(10~15초). 하지만 삭제 위주 PR에서 지적이 1건으로 `medium`의 2건보다 적었고, 비용 절감은 $0.02~$0.03에 그친다.
- **최대 출력 토큰 상한 128,000 유지**: 모델이 허용하는 최댓값이라 설정의 자유가 크다. 하지만 비스트리밍 180초 안에 받을 수 없는 값이라, 크게 잡으면 잘린 응답(건질 지적이 있음)이 아니라 타임아웃(건질 것이 없고 재시도 대상)으로 끝난다.
- **스트리밍으로 바꾸고 상한을 크게 둠**: 타임아웃 걱정 없이 긴 출력을 받는다. 하지만 P1의 실측 출력은 3,400 토큰 이하라 필요가 없고, 어댑터와 테스트가 복잡해진다. 한 번의 호출에 20,000 토큰이 넘게 필요한 경우가 반복되면 이 ADR을 고친다.
- **캐시 지점을 분할 모드에서만 둠**: 단일 모드에서 캐시 쓰기의 추가 비용(입력의 1.25배)을 내지 않는다. 하지만 추가 비용은 약 $0.007이고, 같은 저장소의 PR을 5분 안에 이어 리뷰하면 PR이 달라도 캐시를 읽는다. 모드에 따라 요청 모양이 갈리는 것도 피한다.
- **서버 측 `fallbacks: "default"` 사용**: refusal이 나도 다른 모델이 리뷰를 끝내 불완전 결과가 줄고, Anthropic 안내도 이 모델에 기본으로 켜기를 권한다. 하지만 대체 동작을 재현해 검증하지 못했고, 베타 헤더와 타입 없는 본문 속성에 의존하며, 대체 모델은 단가가 달라 단일 단가를 가정한 `CostCalculator`의 추정 비용이 틀어진다.

## 결과
- P1 스펙의 D-2 제안값(모델, effort, 최대 출력 토큰 기본값, fallback 미사용)이 그대로 확정된다. 바뀌는 것은 최대 출력 토큰의 설정 상한(128,000 → 20,000) 하나다.
- refusal이 나면 리뷰가 종료 코드 3으로 끝난다. 이 모델은 안전 분류기 범주가 넓어 보안 관련 diff에서 나올 수 있다. 도그푸딩에서 refusal이 실제로 나오면 fallback을 다시 검토한다.
- thinking 토큰이 한도에 포함되므로, effort를 올리면 같은 `max_tokens`에서 본문에 쓸 수 있는 양이 줄어든다.
- spend limit에 걸리면 한도가 풀릴 때까지 재시도가 모두 실패한다. 재시도 횟수가 3회로 묶여 있어 낭비는 그만큼이다.
- 후속 작업
  - P1 작업 1.2: Anthropic Java SDK 2.68.0 추가(이 결정으로 막힌 것이 풀린다).
  - P1 작업 2.1: `Configuration.defaults()`의 effort와 최대 출력 토큰, 최대 출력 토큰 범위 검증(1~20,000).
  - P1 작업 13.1: 스키마 직렬화 순서 고정과 그 테스트, 첫 text 블록 선택(effort에 따라 빈 thinking 블록이 앞에 온다).
  - P2 설계의 spike 14번(effort별 응답 시간이 90초를 넘는지)은 이 실측으로 답이 나왔다. 400줄 PR의 effort 기본값을 조정할 필요가 없다.
- 아직 확인하지 않은 것
  - refusal 응답의 실제 모양(`stop_details`)과 fallback으로 넘어갔을 때의 응답.
  - spend limit 429를 일반 429와 구분하는 방법(오류 본문의 코드).
  - 지적이 많은 PR, 분할 모드, 요약 전용 모드의 출력 토큰. P1 작업 20.4의 리허설에서 본다.
  - 같은 입력의 반복 실행 편차와 effort별 리뷰 품질. 도그푸딩의 채택/기각 기록으로 본다.

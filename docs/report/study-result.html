스펙을 먼저 쓰고,
작업 하나씩 구현했다

세 명이 Claude Code로 PR 리뷰 도구 PR Lens를 만들면서 스펙 기반 개발이 실제로 무엇을 바꿨는지 저장소 기록으로 정리한 연구회 결과 보고서입니다.

기간
2026-10-04 ~ 2026-10-26 (첫 커밋부터 마지막 PR #70 머지까지)
참여
3명 (이 보고서에서는 커밋 수 순으로 멤버 1, 2, 3)
결과
P1 CLI 조건부 완료. P2·P3는 착수하지 못함

요약

  • P1 CLI는 조건부 완료입니다. prlens review <PR URL>가 실제 PR을 리뷰해 규칙 근거 지적 17건을 냈습니다. 400줄 실행 시간 측정(20.5)은 API 크레딧이 떨어져 하지 못했습니다. 계획했던 P2(webhook)와 P3(웹)는 시작하지 못했습니다.
  • 스펙은 구현 중에 계속 자랐습니다. 요구사항은 7번만 바뀌었지만 tasks.md는 64번, design.md는 35번 바뀌었습니다. 리뷰가 찾은 "뒤 작업이 스펙만 읽으면 틀리는 것"이 주의 줄 87개로 쌓였습니다.
  • 리뷰는 AI가 했고 사람 리뷰는 거의 없었습니다. AI 리뷰 지적 519건 중 348건(67%)을 반영했고 CI 실패는 0회였습니다. 사람 리뷰는 PR 70건 중 2건이었습니다.
  • 반복된 지적을 규칙과 테스트로 옮겼습니다. PR 25개의 기각 사유를 모아 규칙 6개와 검사 테스트 1개로 만들었습니다(#52, #53). 그 뒤 반복이 줄었는지는 확인하지 않았습니다.
  • 병렬 작업은 공유 타입을 먼저 머지한 뒤에야 일어났습니다. 1~2주차는 한 사람이 PR 대부분을 냈고, 3주차부터 세 사람이 동시에 PR을 냈습니다.

1개요

무엇을 만들었고, 무엇을 확인하려 했는가.

목적

연구회의 목적은 두 가지였습니다.

  • 제품: 팀 컨텍스트(CLAUDE.md, .claude/rules/, PR 본문에 링크된 스펙)를 기준으로 GitHub PR을 리뷰하는 도구 PR Lens를 만듭니다. 단계는 P1 CLI, P2 webhook 자동 리뷰와 저장, P3 웹 조회입니다.
  • 방법: 요구사항·설계·작업 목록을 스펙으로 먼저 쓰고 작업 단위로 Claude Code에 맡기는 팀 개발 방식이 실제로 통하는지 확인합니다.

2스펙 기반 개발 방식

코드보다 스펙을 먼저 쓰고, AI는 스펙의 작업 하나만 보고 구현합니다.

진행 흐름

스펙은 단계마다 폴더 하나이고 네 문서로 나뉩니다. 구현 중에 드러난 사실은 다시 스펙으로 돌아갑니다.

문서담는 것AI가 읽는 방식
README.md (색인)절 위치, 트랙 표, 결정 대기 표항상 먼저 읽음
requirements.md요구사항과 인수 기준(무엇을)작업 본문 끝의 _Requirements: …_ 번호만
design.md패키지, 인터페이스, 데이터 형식, 정확성 속성(어떻게)그 작업의 클래스가 나오는 절만
tasks.md작업, PR 경계, 의존 그래프, 결정 대기가 막는 작업맡은 작업 본문과 Overview·Notes

이 방식을 고른 이유

  • AI가 읽을 범위를 좁히려고: P1 스펙만 2,216줄입니다. 색인과 번호로 필요한 절만 찾아 읽게 해, 세션마다 문서를 통째로 읽지 않게 했습니다.
  • 세 사람이 동시에 일하려고: 트랙 사이의 경계 인터페이스(작업 2.1~2.3)를 먼저 머지하고, 각 트랙은 그 위에서 따로 구현하게 했습니다.
  • AI가 정하면 안 되는 것을 표시하려고: 팀이 정할 항목은 결정 대기(D-n, G-n)로 적고, 구현은 제안값으로만 하게 했습니다.
  • 리뷰 기준을 미리 정하려고: 리뷰어는 작성자의 의도 대신 인수 기준과 대조합니다.

4워크플로

작업 하나는 /task → reviewer → /pr-ready를 거쳐 PR 하나가 됩니다. 사람은 세 번 멈춰서 승인합니다.

단계별 역할

단계하는 일남기는 것
/task상태 확인(완료·진행 중·선행 작업), 브랜치, 계획 승인, 실패 테스트, 구현, 체크박스코드, 테스트, handoff/<번호>.md 메모
reviewer작성자 맥락 없이 diff를 인수 기준·설계·컨벤션과 대조. 결정 대기를 임의로 확정했는지 확인ID가 붙은 표(M1, S1…)와 "뒤 작업에 넘길 것"
/pr-ready바뀐 스택 검증, 리뷰어 호출, 지적 분류, 뒤 작업의 스펙 본문에 주의 줄 반영, 메모 파일 삭제, PR 설명 초안스펙의 주의(n 리뷰)·결정(n) 줄, PR 설명

handoff 메모: 스펙으로 돌아가는 고리

구현 중 "뒤 작업이 스펙만 읽으면 틀리게 되는 것"이 생기면 /task가 메모 파일에 적습니다. /pr-ready는 메모와 리뷰 결과를 합쳐 해당 작업 본문에 - 주의(5 리뷰): … 한 줄을 넣고 메모를 지웁니다. 다음 작업의 세션은 PR 설명을 보지 않아도 스펙에서 이 줄을 읽습니다.

이 고리로 P1 tasks.md에 주의 줄 87개, 결정 줄 38개가 쌓였고, P2 스펙에도 P1 리뷰에서 넘긴 주의 줄 19개가 들어갔습니다. 지금 이 저장소의 handoff/ 폴더는 비어 있습니다(메모 파일은 main에 남지 않게 하므로 다른 멤버의 작업 폴더는 확인하지 않았습니다).

  7. 쓰지 않는 플러그인과 MCP는 프로젝트 단위로 끄세요세션 고정분 중 팀이 손댈 수 있는 부분은 CLAUDE.md보다 설치된 플러그인의 skill 목록이 더 큽니다.근거: 10/27 새 세션 직후 /context 37.2k. 팀 파일 약 3천 대 skill 목록 10k(75개). 이번 프로젝트에서 쓰지 않은 Vercel 플러그인만 skill 약 40개와 에이전트 3개를 더함(약 4.3k로 추정). Claude Code 자체의 도구 정의 18.3k와 시스템 프롬프트 4.3k는 줄일 수 없음. 플러그인을 끈 뒤의 효과는 확인하지 않음
  8. LLM 예산을 일정 계획에 넣으세요실제 API로만 확인할 수 있는 항목은 크레딧이 남아 있을 때 먼저 하세요.근거: 20.5 미실행, P1 조건부 완료

10다음 단계

worktree로 한 사람이 여러 작업을 동시에 돌리고, 오케스트레이션으로 사람의 개입 지점을 줄이는 방향입니다.

worktree 병렬

/task-flow 비교 실험에서 이미 같은 작업을 두 worktree, 두 터미널에서 동시에 구현해 봤습니다(1차는 두 쪽 모두 약 30분대). 다음에는 같은 작업의 A/B가 아니라 의존이 없는 서로 다른 작업을 worktree마다 하나씩 돌립니다. tasks.md의 의존 그래프가 동시에 시작할 수 있는 작업을 알려 주고, /task의 상태 확인이 중복 착수를 막습니다.

  • 이미 있는 것: .worktreeinclude가 gitignore된 비밀값·로컬 설정 파일을 새 worktree로 복사하고, /task는 worktree-<이름> 브랜치를 작업 브랜치 이름으로 바꿉니다
  • 지킬 것: 브랜치를 만들면 바로 push해 다른 worktree와 사람이 진행 중임을 알게 하기
  • 주의할 것: 세션마다 고정 비용(spike 측정 약 5.8만, 10/27 새 세션 37.2k 토큰)이 들고, 사람의 승인 지점(브랜치, 계획, 리뷰 선택)도 worktree 수만큼 늘어납니다

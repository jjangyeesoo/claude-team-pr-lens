# `/task-flow` 계획: 단계를 나눈 task skill

임시 문서입니다. `/task-flow`를 만들기 전의 계획이고, 구현하면 지우거나 `task-workflow.md`의 절로 옮깁니다. 지금의 `/task`(`.claude/skills/task/SKILL.md`)는 이 계획에서 고치지 않습니다.

## 배경
- 마지막 주차에 task 오케스트레이션(매니저가 단계별 에이전트를 관리)을 적용합니다. 처음에는 의존이 없는 작업의 병렬 진행까지 목표로 했으나, 검토 결과 병렬은 보류했습니다(아래 "병렬 실행" 줄).
- 지금의 `/task`는 한 세션이 상태 확인부터 마무리까지 모두 하는 단일 프로세스입니다. 단계별로 다른 모델이나 에이전트에 맡기거나 병렬로 돌리기 어렵습니다.
- `/task`는 그대로 두고, 단계를 에이전트로 나눈 `/task-flow`를 만듭니다. 안정되면 `/task`를 대체하고 이름을 `task`로 바꿉니다.
- 요구: 계획과 리뷰는 opus, 구현은 현재 세션의 모델로 합니다. 첫 PR은 작업(PR 경계) 하나씩만 다루고, 게이트 자동 통과(`--auto`)는 다음 PR에서 합니다.
- 병렬 실행은 검토만 하고 진행하지 않습니다(마지막 절 "병렬 검토"). 겹치는 작업 사이의 의존, 넘길 것의 전달, 작업 트리 공유 문제가 커서, 이번 실습은 작업 하나씩 단계를 나누는 데까지 합니다.

## 결정
| 번호 | 항목 | 결정 |
|---|---|---|
| D1 | 계획 수정 | 계획 파일을 기준으로 합니다. 같은 세션이면 `SendMessage`(planner의 agentId)로 같은 planner에게 보냅니다. 끝난 에이전트도 transcript에서 재개되므로 스펙을 다시 읽지 않습니다. `/clear`나 새 세션 뒤에는 새 planner가 계획 파일과 피드백만 읽고 고칩니다. 메인 세션은 계획을 직접 고치지 않습니다. fork는 쓰지 않습니다(부모 모델로 돌아서 구현 세션이 다른 모델이면 opus 조건이 깨지고, 메인에는 스펙 컨텍스트가 없습니다) |
| D2 | 계획 파일 | `docs/specs/<스펙>/handoff/<번호>-plan.md`(`<번호>`는 브랜치 이름의 번호). 상태 줄 아래를 `## 공통`과 `## 슬라이스 N (<하위 작업 번호>)` 절로 나눕니다(D10). 공통 절: 입력 근거(인수 기준 번호, `design.md` 절 제목), 결정과 이유, 슬라이스 순서와 이유, 요구사항 변경, 질문, 수정 이력. 슬라이스 절: 계획 본문, 주의·미정 대응(아래 "주의·미정 대응"), 테스트 목록(아래 "테스트 목록"). **커밋하지 않습니다**: `.gitignore`에 `docs/specs/*/handoff/*-plan.md`와 `*-review.md`를 더합니다(`-context-review.md`도 이 패턴에 걸림, D5). 커밋하지 않은 파일이 남아 `/pr-ready` 1번이 멈추는 것을 막기 위해서입니다. 그래서 계획 파일은 그 PC에만 있고, 다른 PC나 다른 사람은 이어받지 못합니다(메모 파일 `<번호>.md`는 지금처럼 커밋합니다) |
| D3 | 구조 | 메인 세션이 매니저(상태 확인, 브랜치, 사람 게이트, 결과 취합)입니다. `planner`(opus), `implementer`(현재 모델, `model: inherit`), `reviewer`·`context-reviewer`(opus, 기존 에이전트. 어느 쪽을 부를지는 `/pr-ready` 3번의 경로 규칙을 그대로 따름)에게 단계를 맡깁니다. 워커 1명짜리 매니저입니다(병렬은 "병렬 검토" 절에서 검토만 함). **planner와 implementer는 frontmatter `background: true`로 백그라운드에 고정하고, 구현 검증은 implementer가 끝날 때 합니다**(아래 "구현 중 검증"). 기본 실행 모드는 세션 설정(fork 모드)에 따라 포그라운드일 수도 있다고 문서에 나오므로, 전제를 고정하려고 명시합니다. 백그라운드면 매니저 턴이 implementer보다 먼저 끝나고, 그대로 두면 메인의 Stop hook이 실패 테스트만 있는 중간 상태를 검증해 매니저를 막고, 메인 세션이 그 실패를 고치려 들어 implementer와 같은 파일을 건드릴 수 있습니다. 백그라운드 서브에이전트가 끝나면 완료 알림이 메인 세션을 깨워 매니저가 이어 갑니다(이 환경에서 확인함: 계획 검토 에이전트 세 번 모두 사용자 입력 없이 완료 보고가 도착해 이어서 응답함). 백그라운드 서브에이전트의 권한 프롬프트(planner·implementer의 Write·Edit, implementer의 `git add`·`git commit` 등)는 메인 세션에 에이전트 이름과 함께 뜨므로 사용자가 메인 세션에서 처리합니다(allow 추가는 하지 않음). 기존 `reviewer`·`context-reviewer`는 `/pr-ready`와 같이 쓰므로 frontmatter를 바꾸지 않고, allow에 없는 `git fetch`는 리뷰어를 부르는 쪽(매니저, `/pr-ready`)이 먼저 실행합니다 |
| D4 | 리뷰 | implementer가 작업 브랜치에 커밋합니다. 비교 기준은 어디서나 `origin/main`으로 통일합니다: reviewer는 브랜치 인자를 받으면 `origin/main...<브랜치>`, 인자가 없으면 `origin/main...HEAD`를 보고, `/pr-ready` 1번의 변경 범위 확인과 G3의 줄 수 계산도 같은 기준을 씁니다. 로컬 `main`이 뒤처져 diff가 부풀지 않게 하기 위해서입니다. 비교 전에 `git fetch origin`을 하되, reviewer 안이 아니라 부르는 쪽(매니저, `/pr-ready`)이 합니다(D3). `origin`이 없는 저장소는 `/task`처럼 로컬 `main`을 대신 씁니다. 리뷰는 모든 슬라이스가 끝난 뒤 경계 전체에 대해 합니다(D10). "반드시 수정"은 경계 전체를 고치는 implementer 하나에게 넘깁니다(같은 세션이면 마지막 슬라이스의 implementer에게 `SendMessage`, 아니면 새 implementer) |
| D5 | 이중 리뷰 방지 | 매니저가 리뷰어마다 리뷰 파일을 따로 저장합니다: `reviewer`는 `handoff/<번호>-review.md`, `context-reviewer`는 `handoff/<번호>-context-review.md`. 두 리뷰어는 영역(코드와 지침)이 달라 결과를 합치지 않습니다. 리뷰 파일에는 리뷰어가 쓴 ID(`M1`, `S1`)를 그대로 저장하고, 머리글자는 파일로 정합니다(`-review.md`는 `R`, `-context-review.md`는 `C`). implementer 전달, 상태 줄, G3 보고에서는 늘 머리글자를 붙인 형식(`R-M1`, `C-S2`)을 써서, 한 번에 넘겨도 구분되고 기계로 비교할 수 있게 합니다. 수정 뒤의 확인 리뷰는 첫 리뷰를 돌린 리뷰어 **모두**에게 돌립니다(지적이 없던 쪽도. 수정이 그 영역을 건드렸을 수 있고, 파일의 SHA를 `HEAD`에 맞춰야 `/pr-ready`가 재사용하므로). 각 파일은 덮어쓰지 않고 리뷰마다 `## 리뷰 N (SHA <sha>, 첫/확인)` 절을 이어 씁니다. 확인 리뷰는 첫 리뷰의 "선택"과 "뒤 작업에 넘길 것"을 다시 만들지 않으므로, 덮어쓰면 그것과 리뷰 횟수가 사라지기 때문입니다. 리뷰 횟수는 절 수로 셉니다. 이 파일은 커밋하지 않으므로(D2) 저장해도 `HEAD`가 바뀌지 않습니다. `/pr-ready`는 그 리뷰어의 파일이 있고 **마지막 절**의 SHA가 `HEAD`와 같을 때만 재사용하고(5번의 "뒤 작업에 넘길 것"은 첫 절의 항목에 확인 리뷰 절들의 판정을 절 순서대로 적용해 읽음), 아니면 지금처럼 그 리뷰어를 돌립니다. 기존 `/task`는 이 파일들을 만들지 않으므로 기존 흐름은 바뀌지 않습니다. 기존 메모 파일(`<번호>.md`)과 이름도 겹치지 않습니다 |
| D6 | 규칙의 원본 | `/task-flow`가 `/task`를 대체할 것이므로 `/task`의 번호를 참조하지 않고 새 파일을 원본으로 씁니다. 단계 규칙은 에이전트 정의에, `SKILL.md`에는 매니저 절차만 둡니다. 공존 기간에는 `.claude/rules/context/editing.md`의 맞물린 파일 목록에 "`/task` ↔ `/task-flow`(대체 전까지 함께 고친다)"를 더합니다 |
| D7 | 사람 게이트 | G1 브랜치 이름 확인, G2 계획 승인, G3 리뷰와 수정 뒤 최종 보고. 각 게이트에 자동 통과 조건을 적어 두어 다음 PR의 `--auto`가 쓰게 합니다. 조건은 planner나 implementer의 판단이 아니라 매니저가 기계로 확인할 수 있는 값으로 정합니다(아래 "게이트 조건"). 게이트 밖의 사람 확인이 둘 더 있습니다: 첫 리뷰 뒤 고칠 "선택" ID 확인(`--auto`에서는 묻지 않고 G3 보고에 기록), 슬라이스가 다음 슬라이스의 계획을 바꿨을 때의 계획 재승인(G2와 같은 확인, `--auto`에서도 멈춤, D10) |
| D8 | 작업 상태 | 계획 파일 맨 위에 매니저만 고치는 상태 줄을 둡니다(아래 "작업 상태"). 매니저가 상태를 대화 컨텍스트에만 두면 `/clear`나 압축 뒤에 어디까지 했는지 잃기 때문입니다. 상태 줄과 산출물(브랜치, 커밋, `-review.md`)이 어긋나면 **알리고 멈춥니다**. 어긋났을 때의 상태 줄은 사용자가 확인한 뒤에 고칩니다 |
| D9 | 테스트 작성 | 실패 테스트는 implementer가 씁니다. 테스트 작성 에이전트를 따로 두지 않습니다. 따로 두면 빨간 트리로 끝나는 에이전트가 하나 더 생겨 "구현 중 검증"의 표시와 종료 검증을 그 에이전트용으로 다시 짜야 하고, 시그니처처럼 구현하면서 정해지는 것 때문에 두 에이전트가 오가게 됩니다. 대신 분리로 얻으려던 것을 셋으로 나눠 얻습니다. ① 인수 기준에서 나온 테스트: planner가 "테스트 목록"을 정하고 G2에서 사람이 승인합니다 ② 테스트를 약하게 하지 않음: implementer가 구현 전에 실패 테스트(와 스텁)만 담은 `test:` 커밋을 따로 남기고, 그 뒤 테스트 diff를 G3 조건으로 봅니다(PR은 squash 머지하므로 이 빨간 커밋은 `main` 히스토리에 남지 않습니다) ③ 대조: reviewer가 테스트 목록과 실제 테스트, `test:` 커밋 뒤 테스트 변경의 이유를 확인합니다. 리뷰에서 "구현을 따라 쓴 테스트"나 "인수 기준을 빠뜨린 테스트"가 반복되면 분리를 다시 검토합니다 |
| D10 | 작업 단위와 슬라이스 | `/task`처럼 상위 작업 번호나 PR 경계 안의 번호(예: `7.3`)를 받으면 그 번호가 속한 PR 경계 전체(`7.2~7.5`)를 대상으로 합니다. 계획(G2), 리뷰, 수정, G3는 **경계 단위**, implementer·`test:` 커밋·종료 검증은 **슬라이스 단위**입니다. 슬라이스는 planner가 정합니다(구현 작업 하나와 그것을 검증하는 `*` 작업, 예: `7.2+7.3`, `7.4+7.5`). 경계 하나를 implementer 하나가 맡으면 한 슬라이스의 `BLOCKED`가 끝난 슬라이스까지 빨간 트리에 묶고, 컨텍스트가 길어져 뒤 슬라이스에서 계획과 주의를 놓치기 쉽기 때문입니다. 슬라이스마다 새 implementer를 띄우고, implementer는 계획 파일의 `## 공통`과 자기 `## 슬라이스 N` 절만 읽습니다(다른 슬라이스를 미리 건드리지 않게). 앞 슬라이스가 남긴 것은 지금 `/task`처럼 메모 파일(`<번호>.md`)과 커밋으로 넘깁니다. implementer 보고의 `다음 슬라이스 영향`이 `있음`이면 매니저는 다음 슬라이스로 넘어가지 않고 같은 planner에게 그 슬라이스 절을 고치게 한 뒤(D1) 사람이 다시 승인합니다. 계획 파일은 implementer가 고치지 않습니다. 리뷰를 슬라이스마다 하지 않는 것은, reviewer가 경계의 일부만 보면 나머지를 누락으로 오판하고, `/pr-ready`가 마지막 SHA로 재사용하므로 결국 전체 리뷰를 한 번 더 하게 되기 때문입니다. 슬라이스가 하나뿐인 경계(예: `7.1`)는 슬라이스 절 하나로 같은 흐름을 탑니다 |

### 작업 상태
G1을 통과하면 매니저가 상태 줄만 있는 계획 파일 골격을 만들고, planner는 그 아래 본문만 채웁니다. 상태 줄은 매니저만 고칩니다.
```
상태: 구현 중
브랜치: feat/t2-p1-7.2-pr-fetcher
승인: G2 2026-10-20
planner: <agentId> · implementer: <agentId>
슬라이스: 2/2 (7.4+7.5)
실패 테스트: 7.2=<커밋 SHA>, 7.4=<커밋 SHA>
고칠 선택: 없음
남긴 반드시 수정: 없음
```
- `고칠 선택`은 첫 리뷰 뒤 사용자가 고르라고 한 "선택" ID입니다(예: `R-S1, C-S2`). 묻고 답을 기다리는 동안은 `묻는 중`, 고르지 않았거나 "선택"이 없으면 `없음`입니다. 수정을 넘길 때와 확인 리뷰를 부를 때 이 값을 함께 넘깁니다
- `슬라이스`는 지금 구현 중이거나 마지막으로 끝낸 슬라이스입니다. 매니저가 implementer를 띄울 때 고칩니다
- `승인`은 G2를 통과할 때 매니저가 적습니다. 그 전에는 `승인: 없음`입니다
- `실패 테스트`는 슬라이스마다 implementer가 보고한 `test:` 커밋입니다(슬라이스의 첫 하위 작업 번호=SHA). 매니저가 그 커밋이 이 브랜치에 있고, 제목이 `test:`로 시작하고, 테스트가 아닌 파일은 그 슬라이스 "테스트 목록"의 `스텁` 열에 적힌 것만 담았는지 확인한 뒤 적습니다. 그 전이나 테스트 목록이 "없음"인 슬라이스는 `<번호>=없음`, 테스트만 쓰는 슬라이스는 `<번호>=해당 없음(<그 슬라이스 첫 커밋 SHA>)`입니다. 이 SHA는 매니저가 implementer 완료 때 `origin/main..HEAD`에서 앞 슬라이스까지 상태 줄에 적힌 커밋 다음 커밋으로 찾아 적고, G3의 약화 검사 기준으로 씁니다(D9, "테스트 목록")
- `남긴 반드시 수정`은 "수정 필요"에서 사용자가 그대로 두라고 한 ID입니다(예: `R-M2, C-M1`). 그 밖에는 `없음`입니다
- agentId는 같은 세션에서 `SendMessage`가 될 때만 씁니다. `/clear`나 새 세션 뒤에는 새 에이전트를 띄웁니다(D1)

`/task-flow <스펙> <번호>`를 다시 실행하면 매니저는 먼저 아래로 판단합니다.
- 계획 파일이 있음: 상태 줄을 읽고 위 표의 "재개 시 할 일"을 합니다. G1은 건너뜁니다
- 계획 파일은 없고 이 작업의 브랜치가 있음: `/pr-ready`를 이미 돌렸거나, 다른 PC에서 시작한 작업입니다. 브랜치의 커밋과 PR 여부(`gh pr list --head <브랜치>`)를 알리고 멈춥니다. 어떻게 이어 갈지는 사용자가 정합니다
- 둘 다 없음: 처음부터 시작합니다

### 게이트 조건
`--auto`일 때도 아래 중 하나라도 맞으면 멈춥니다. 이번 PR에서는 모든 게이트에서 멈추고, 이 조건은 G2·G3 보고에 "자동이었다면 멈췄을 이유"로만 출력합니다.

|---|---|---|
| G1 | 같은 `-<단계>-<번호>-` 또는 `/<단계>-<번호>-` 패턴의 **다른** 브랜치가 원격이나 로컬에 있음(다른 사람이 진행 중). 이 작업의 계획 파일에 적힌 브랜치는 제외하고, 재개할 때는 G1을 건너뜀 | `git fetch --prune origin` 뒤 `git branch -a`에서 이름 패턴 검사(`/task` 1.1·1.3과 같음) |
| G2 | 작업이 결정 대기(D-n, G-n)에 걸림 | `tasks.md` Notes "막는 작업" 표의 행 가운데, 항목이 확정되지 않은 행에 경계 안 하위 작업 번호가 있음. 확정 여부는 항목 이름에 `확정`이 있거나 그 행이 링크한 ADR이 `docs/adr/README.md`에 대체되지 않은 결정으로 올라 있는지로 봅니다(P1 D-2는 문구에 `확정`이 없고 ADR 0005로 확정됨). 스펙 색인의 결정 대기 표는 그 D/G의 제안값을 보여 주는 데만 씀. `tasks.md` Notes에 "막는 작업" 표가 없는 스펙(지금 P2)이면 판정할 수 없으므로 멈추고, 표를 먼저 더하라고 알림 |

| 슬라이스 사이 | 다음 슬라이스의 계획이 바뀜 | implementer 보고의 `다음 슬라이스 영향:`이 `없음`이 아님(D10. G2와 같은 사람 확인이며 `--auto`에서도 멈춤) |

### 구현 중 검증
> **구현하면서 바뀜 (2026-10-18, 체크리스트 0 결과).** SubagentStop은 서브에이전트의 보고(`SubagentHandback`) 뒤에 와서 exit 2로 붙잡을 수 없었습니다. 그래서 아래를 바꿨고, 구현된 동작의 원본은 `docs/guide/claude-code-setup.md` "구현 중 검증"입니다.
> - 종료 검증은 PreToolUse(matcher `SubagentHandback`)에서 합니다. `BLOCKED:` 판별은 보고 원문(`tool_input.message`)으로, 재시도 횟수는 표시 파일에 셉니다. SubagentStart·SubagentStop hook은 쓰지 않습니다
> - 실행 중 판정은 표시 파일이 아니라 메인 Stop 입력의 `background_tasks`(실행 중인 implementer)로 합니다. 표시 파일은 `blocked`·`failed`(끝났지만 트리가 빨감)에만 씁니다. 그래서 "실재 확인"과, 멈춘 implementer의 표시가 12시간 남는 문제가 없어졌습니다
> - 매니저의 결과 확인은 `VerifyOnStop.java --check <agentId>`로 합니다(agent_id, 스택 결과, 내용 해시, 끝날 때 깨끗했는지)
> - handback 모드는 기록이 없을 때 `baseline`을 쓰지 않고 검증합니다(이 브랜치가 건드리지 않은 스택은 `pass-nothing-to-verify`)

검증을 메인의 Stop에서 implementer의 SubagentStop으로 옮깁니다. 검증 명령과 판정은 지금의 `VerifyOnStop.java`를 그대로 씁니다.

hook은 모두 `settings.json`에 둡니다(SubagentStart·SubagentStop, matcher `implementer`). 에이전트 frontmatter의 `hooks`로도 걸 수 있지만, 설정을 한 파일에 모으고 판정 로직도 `VerifyOnStop.java` 한 곳에 두기 위해서입니다.

1. **시작 표시**: SubagentStart hook이 표시 파일 `build/claude-verify/implementer-marker.json`에 입력의 `agent_id`, `session_id`, 시작 시각, 메인 세션의 `transcript_path`를 적습니다. 이름은 같은 폴더의 검증 상태 파일(`state.properties`, `*.log`)과 구분합니다
2. **구현 중 메인 Stop**: `VerifyOnStop`은 표시가 유효하면 검증하지 않고 "implementer `<agentId>` 실행 중이라 검증을 건너뜁니다(시작 `<시각>`)"를 `systemMessage`로 알립니다. 유효하지 않으면 지금처럼 검증합니다
3. **implementer 종료 검증**: SubagentStop hook이 `VerifyOnStop`을 돌립니다
   - 입력의 `last_assistant_message`가 `BLOCKED:`로 시작하면 검증하지 않습니다. 질문하려고 멈춘 implementer를 붙잡으면 `BLOCKED` 흐름이 깨지기 때문입니다(트리는 빨간 채로 남고, 매니저가 질문을 사용자에게 전합니다). 표시는 지우지 않습니다(4번)
   - 실패하면 exit 2로 implementer를 붙잡아 고치게 하고, 두 번째 실패(`stop_hook_active`)에서는 놓아줍니다
   - 결과가 `pass`·`pass-nothing-to-verify`이면 항상 그 뒤 `git status --porcelain`을 보고, 비어 있지 않으면 exit 2로 "포맷 변경(또는 커밋하지 않은 변경)을 커밋하라"고 돌려보냅니다. `spotlessApply`와 `npm run verify`(`prettier --write`)는 파일을 고치는데, implementer는 커밋한 뒤에 끝나므로 이 변경이 커밋되지 않은 채 남아 "리뷰 중"의 교차 확인, reviewer의 diff, `/pr-ready` 1번을 함께 깨기 때문입니다. implementer가 커밋 직전에 포맷만 돌리는 것이 1차 대책이고(implementer.md), 이것은 놓친 경우를 잡습니다. 내용 해시는 `docs`, `.claude`, `*.md`를 빼므로 `tasks.md` 체크박스만 커밋하지 않은 경우도 `pass-nothing-to-verify`가 되는데, 이 검사가 그것도 잡습니다
   - 결과는 스택(backend, web)마다 `pass`(검증 통과), `pass-nothing-to-verify`(마지막 통과와 내용이 같거나 문서만 바뀜), `baseline`(기록이 없고 트리가 깨끗한 첫 실행이라 검증 없이 기준선만 기록함, `VerifyOnStop.java:122`), `fail`, `unavailable`(도구를 실행하지 못함. 지금 `VerifyOnStop`은 이때도 exit 0), `blocked`(`BLOCKED` 건너뛰기) 가운데 하나로 적습니다. G3는 `pass`·`pass-nothing-to-verify`만 통과로 봅니다. 결과(입력의 `agent_id`, 스택별 결과와 내용 해시, 종료 시각)를 `build/claude-verify/implementer-result.json`에 남깁니다. 매니저는 G3에서 이 파일의 `agent_id`가 상태 줄의 `implementer`와 같을 때만 검증 증거로 씁니다. 다르면 이전 실행의 결과이므로 "결과 없음"으로 보고 멈춥니다. 통과하면 통과 기록(내용 해시)도 남으므로 그 뒤 메인 Stop은 같은 내용을 다시 검증하지 않습니다
4. **표시 해제**: 통과하면 3번의 hook이 표시를 지웁니다. `BLOCKED`와 두 번째 실패에서는 지우지 않고 표시의 상태를 `blocked`·`failed`로 바꿉니다. 트리가 빨간 채로 남으므로, 지우면 매니저가 턴을 끝낼 때 메인 Stop이 빨간 트리를 검증해 매니저를 붙잡고, 매니저가 implementer의 파일을 고치게 되기 때문입니다(D3가 막으려던 일). 메인 Stop은 이 상태의 표시도 유효로 보고 건너뛰되 안내에 그 상태를 적습니다. 이 표시는 매니저가 `SendMessage`로 재개할 때 다시 쓰거나(5번), 사용자가 그 작업을 중단하기로 했을 때 매니저가 지웁니다. 붙잡는 동안(exit 2)에도 지우지 않습니다. 실행 중인 표시를 시간으로 만료시키지 않는 것은 이 해제가 있기 때문입니다(아래 "남은 표시 정리")
5. **재개할 때**: `SendMessage`로 implementer를 다시 깨울 때(`BLOCKED`의 답, "반드시 수정") SubagentStart가 다시 발생하는지는 확인되지 않았습니다. 발생하지 않으면 매니저가 `SendMessage` 직전에 `java .claude/hooks/VerifyOnStop.java --mark <agentId>`로 표시를 씁니다. 이 표시에는 메인 `transcript_path`가 없으므로(그 값은 SubagentStart 입력에만 옴) "실재 확인"을 하지 않고, 출처를 `mark`로 적어 SubagentStart가 쓴 표시와 구분합니다. 이 명령은 Bash로 표시를 만드는 우회로와 같은 능력이므로, 아래 "드러내기"로 보이게 하는 것이 대책입니다. allow에 없으므로 실행할 때 권한 프롬프트가 뜹니다

implementer는 전체 검증(`spotlessApply test`, `npm run verify`)을 직접 돌리지 않습니다. 직접 돌린 검증은 통과 기록을 남기지 않아 종료 검증이 한 번 더 돌기 때문입니다. 실패 테스트 확인과 구현 중 확인은 그 테스트만 돌립니다.

**우회로 대책.** 표시 파일은 일반 파일이라, 메인 세션이 Bash로 만들기만 해도 Stop 검증을 끌 수 있습니다. 지금은 검증을 끄려면 승인 프롬프트가 뜨는 `.claude/` 파일을 고쳐야 하므로, 이 변경은 hook 완화에 해당합니다(`editing.md`에 따라 구현 PR에서 이유를 설명하고 승인받습니다). 다음으로 우회를 어렵게 하고, 건너뛸 때마다 드러나게 합니다.
- **내용 검사**: 표시 파일에 agent ID와 시작 시각이 형식대로 있어야 유효합니다. 빈 파일이나 형식이 다른 파일은 무시하고 검증합니다
- **세션 확인**: 메인 Stop은 hook 입력의 `session_id`가 표시의 `session_id`와 다르면 표시를 무효로 보고 검증합니다. implementer가 SubagentStop 없이 끝난 뒤(세션 종료, 프로세스 중단) transcript 파일은 남으므로, 실재 확인만으로는 다음 세션에서도 표시가 유효로 보이기 때문입니다. `--mark` 표시는 세션 ID를 모르므로 이 검사를 하지 못하고, SubagentStop의 해제와 12시간 기한에만 기댑니다(한계). `/clear` 뒤에는 세션이 바뀌어 `blocked`·`failed` 표시도 무효가 되므로, 매니저가 재개할 때 `--mark`로 다시 씁니다(상태 표 "구현 중"). 또 `claude --resume`·`--continue`로 이어 갈 때 `session_id`가 유지된다면 이 검사가 막는 것은 새 세션뿐입니다. 이는 확인되지 않았으므로 검증 체크리스트 0번에서 확인합니다
- **남은 표시 정리**: 표시는 4번의 해제로 지우므로, 시간 기한은 SubagentStop 없이 남은 표시(implementer 비정상 종료, 세션 중단)를 정리하는 용도로만 둡니다. 시작 시각에서 12시간이 지난 표시는 무시합니다. 1시간처럼 짧게 잡으면 Gradle 테스트를 여러 번 돌리는 긴 구현이 끝나기 전에 표시가 만료되어, 메인 Stop이 구현 도중의 상태를 검증하는 문제가 다시 생깁니다
- **실재 확인** (SubagentStart가 쓴 표시만, `mark` 표시는 제외): 표시에 적힌 메인 `transcript_path`에서 서브에이전트 transcript 경로(`<세션>/subagents/agent-<agentId>.jsonl`)를 만들어, 파일이 **있을 때만** 유효로 봅니다. 수정 시각은 보지 않습니다. Gradle 테스트처럼 몇 분 걸리는 명령을 실행하는 동안에는 transcript에 쓰기가 없어, 수정 시각으로 판단하면 실행 중인 implementer의 표시가 무효가 되기 때문입니다. SubagentStop 입력에는 `agent_transcript_path`가 직접 오므로, 첫 실행에서 이 값과 만든 경로가 같은지 확인합니다. 경로를 만들 수 없으면 이 검사는 빼고 나머지로 운영합니다
- **편집 보호**: `ProtectFiles`에 `build/claude-verify/` 경로를 더해 Edit·Write로는 만들거나 고치지 못하게 합니다. Bash로 만드는 것은 막지 못하므로 보조 수단입니다
- **드러내기**: 건너뛸 때마다 2번의 `systemMessage`가 사용자에게 보입니다(지금 `VerifyOnStop`도 알림에 `systemMessage`를 쓰고 있음). implementer를 띄우지 않았는데 이 안내가 나오면 우회를 의심할 수 있습니다

**신뢰 수락.** 프로젝트의 hook과 에이전트는 이 폴더에서 워크스페이스 신뢰 대화상자를 수락한 뒤에만 돕니다. 수락하지 않았으면 오류 없이 조용히 돌지 않으므로 첫 실행 전에 확인합니다.

### 주의·미정 대응
planner는 작업 본문의 `주의`·`미정` 줄마다 한 행을, 그 하위 작업이 속한 슬라이스 절에 씁니다. 본문에 없으면 `없음` 한 줄을 적습니다(파싱 실패와 구분하기 위해서입니다).

```
| 본문 줄 | 종류 | 대응 | 내용 |
|---|---|---|---|
| tasks.md:153 | 주의 | 따름 | getTree는 404면 GitHubApiException → 테스트 getTree_404_throws |
| tasks.md:154 | 미정 | 정함 | 알 수 없는 type은 FileFetch.Unsupported로 보냄 |
| tasks.md:157 | 주의 | 코드와 다름 | 실행기는 음수 delay를 0초로 보지 않음(RetryExecutor:42) → "질문" 절로 |
| tasks.md:158 | 미정 | 질문 | 요구사항을 바꿔야 할 수 있음 → "질문" 절로 |
```

- "대응"은 `따름`, `정함`, `코드와 다름`, `질문` 넷 가운데 하나입니다. `코드와 다름`과 `질문`은 "질문" 절에도 적습니다
- 경로 대조를 쓰지 않는 이유: "주의" 줄은 대부분 파일 경로가 아니라 클래스·메서드 이름(`GlobMatcher.validate`, `RepoPaths.normalize`)을 가리킵니다. 경로로 대조하면 경로가 없는 줄은 늘 통과하고, "이렇게 써라"는 주의(고치지 않는 파일)는 계획을 제대로 따라도 멈춥니다
- 판단(코드와 다른지)은 planner가 하고, 매니저는 빠짐없이 다뤘는지와 멈출 값인지를 셉니다(D7)
- G3 보고와 마무리(지금 `/task` 3.8번의 "주의"·"미정" 정리)에서도 이 표를 체크리스트로 씁니다

### 테스트 목록
planner는 implementer가 먼저 쓸 실패 테스트를 슬라이스 절마다 정합니다(D9, D10). 테스트 코드는 쓰지 않고 목록만 씁니다.

```
| 테스트 | 인수 기준 | 기대 실패 | 스텁 |
|---|---|---|---|
| GitHubClientTest.getTree_404_throws | 17.3 | GitHubApiException이 던져지지 않음 | — |
| GitHubClientTest.getTree_truncated_warns | 22.5 | truncated가 false로 나옴 | backend/src/main/java/com/prlens/github/TreeResult.java (`truncated()`가 false를 돌려주는 빈 구현) |
```

- 작업 본문 `_Requirements: …_`의 인수 기준마다 테스트가 하나 이상 있어야 합니다(번호 형식도 그대로). 테스트로 확인할 수 없는 기준(문서, 설정만 바꾸는 작업)은 `없음`과 그 이유를 적습니다. G2가 이 짝을 셉니다
- "기대 실패"는 assertion 실패여야 하고 컴파일 실패는 쓰지 않습니다(지금 `/task` 3.6번과 같음). 컴파일 실패로 커밋하면 그 모듈의 테스트가 모두 깨져 기대대로 실패하는지 확인할 수 없기 때문입니다
- 새 타입이나 메서드가 없으면 컴파일되지 않는 테스트는 `스텁` 열에 빈 구현을 둘 파일을 적습니다. 스텁은 기본값(`false`, 빈 목록, `null` 등)을 돌려주는 것이 원칙입니다. 예외를 던지면 assertion 실패가 아니라 오류가 나기 때문입니다. `UnsupportedOperationException`은 다른 예외를 기대하는 테스트에서만 씁니다. implementer는 `test:` 커밋에 이 파일만 테스트와 함께 담을 수 있고, G3가 이 열로 구현이 섞였는지 봅니다. 필요 없으면 `—`
- "기대 실패"는 implementer가 실패 테스트를 돌려 그 이유로 실패하는지 확인하는 기준입니다. 다른 이유로 실패하면(설정 오류, 다른 테스트의 실패) 테스트를 고친 뒤 커밋합니다
- implementer는 테스트 이름이나 위치를 바꿀 수 있지만, 바꾼 것과 이유를 보고에 적습니다. 계획 파일은 고치지 않습니다(planner의 파일)
- 슬라이스의 하위 작업이 모두 테스트만 쓰는 작업(`*` 속성 테스트, 통합·골든·스모크 테스트)이면 구현이 이미 있어 "기대 실패"를 낼 수 없습니다(`/task`의 "`*` 작업은 구현이 이미 있으므로 테스트만 쓴다"). planner는 그 슬라이스 절에 `실패 테스트: 해당 없음(<이유>)`을 적고, implementer는 `test:` 커밋 없이 테스트를 씁니다. 남용하지 않게 매니저는 이 값을 G2 보고에 따로 보여 줍니다

### 단계 파이프라이닝 (worktree 없이 가장 가까웠던 안)

```

사람        :  G2(8, 10 일괄)   G3(7)        G3(8)
```

- **계획 병렬**: 작업 번호를 여러 개 받아 planner를 백그라운드로 동시에 띄웁니다. planner는 gitignore된 계획 파일만 쓰므로 같은 작업 트리에서 돌 수 있습니다. G2는 한 번에 받습니다

현재 브랜치를 PR 전에 점검한다.

1. `git fetch origin` 뒤 `git status`, `git diff origin/main...HEAD --stat`으로 변경 범위를 확인한다(`origin`이 없으면 이 파일의 `origin/main`을 로컬 `main`으로 읽는다). 로컬 `main`이 뒤처져 diff가 부풀지 않게 하기 위해서이고, 이 fetch가 3번 리뷰어의 비교 기준도 맞춘다(리뷰어는 fetch하지 않는다).
   - 커밋하지 않은 변경이 있으면 먼저 알리고 멈춘다. reviewer는 `git diff origin/main...HEAD`로 커밋된 변경만 본다. `/task-flow`의 계획·리뷰 파일(`handoff/*-plan.md`, `*-review.md`)은 gitignore되어 여기에 나오지 않는다.
   - PR 단위는 `tasks.md`의 상위 작업 하나다. 그 작업에 "PR 경계"가 적혀 있으면 이 브랜치가 경계 하나에 해당하는지 확인한다.
   - 크기는 `src/main` 변경만 센다(테스트, 픽스처, 문서 제외). 400줄을 넘으면 `tasks.md`의 PR 경계로 나눌 수 있는지 먼저 보고, 나눌 수 없으면 PR 설명에 넣을 이유를 한 줄 제안한다.
2. 바뀐 스택만 검증하고 결과(통과 수, 실패 여부)를 증거로 기록한다.
   - `backend/`가 바뀌었으면 `backend/`에서 `./gradlew spotlessApply test`
   - `web/`이 바뀌었으면 `web/`에서 `npm run verify`와 `npm run build`
   - backend 응답 DTO가 바뀌었는데 `web/src/lib/api/types.ts`가 그대로면 짚어 준다
3. 바뀐 경로에 따라 서브에이전트로 diff를 리뷰한다.
   - `.claude/`나 `CLAUDE.md`(하위 폴더의 것 포함)가 바뀌었으면 `context-reviewer`로 리뷰한다. 함께 바뀐 `docs/`, `.github/`, 루트 `README.md`도 `context-reviewer`가 본다. 바뀐 skill·agent를 실행해 본 결과가 있으면 함께 넘기고, 없으면 없다고 적는다(6번의 검증 증거에도 그렇게 적는다).
   - `backend/`나 `web/`이 바뀌었으면 `reviewer`로 리뷰한다. 관련 스펙이 있으면 스펙 폴더 경로(`docs/specs/<이름>/`)와 작업 번호를 함께 넘긴다.
   - `.claude/hooks/`의 Java 파일이 바뀌었으면 `backend/`나 `web/`이 그대로여도 `reviewer`로도 리뷰한다.
   - `context-reviewer`와 `reviewer` 조건에 모두 해당하면 둘 다 실행한다. 어느 조건에도 해당하지 않으면(문서만 바뀐 브랜치) `reviewer`만 쓴다.
   - `/task-flow`가 남긴 리뷰 파일은 리뷰어마다 재사용한다. 이 브랜치 작업 번호(브랜치 이름의 번호)의 `docs/specs/<스펙>/handoff/<번호>-review.md`(reviewer), `<번호>-context-review.md`(context-reviewer)가 있고 그 파일 **마지막 절** 제목 `## 리뷰 N (SHA <sha>, …)`의 SHA가 `git rev-parse HEAD`와 같으면 그 리뷰어는 다시 돌리지 않는다. 아니면 그 리뷰어만 지금처럼 돌린다. `<스펙>`은 `docs/specs/*/handoff/<번호>-plan.md` 가운데 상태 줄 `브랜치:`가 현재 브랜치인 파일의 스펙 폴더다(작업 번호는 스펙마다 겹칠 수 있고, gitignore된 파일은 브랜치를 바꿔도 남는다). 그런 계획 파일이 없으면 재사용하지 않는다.
4. 리뷰 결과를 "반드시 수정", "선택", "뒤 작업에 넘길 것"으로 나눠 보여 준다(`context-reviewer`는 앞의 두 그룹만 보고한다). 리뷰어는 "반드시 수정"과 "선택"을 ID가 붙은 표로 보고한다(`reviewer.md` 4번). 두 리뷰어의 결과를 한 번에 보여 줄 때는 `reviewer`의 ID에 `R-`, `context-reviewer`의 ID에 `C-`를 붙여 구분한다.
   - 재사용하지 않은 리뷰어: "반드시 수정"은 고친다. "선택"은 표(추천, 수정안, 이유)를 보여 주고 고칠 ID를 묻는다. 답이 없거나 고르지 않으면 고치지 않는다.
   - 재사용한 리뷰 파일: "반드시 수정"은 그 파일 마지막 절의 표만 쓴다. 계획 파일(`<번호>-plan.md`) 상태 줄의 `남긴 반드시 수정`에 있는 ID는 고치지 않고 보여 주기만 하고 PR 설명에 적는다. 그 밖의 ID(계획 파일이 "수정 필요"에서 멈춘 경우 등)는 재사용하지 않은 리뷰어의 "반드시 수정"과 같이 고친다. "선택"은 다시 묻지 않고, 첫 절의 "선택" 가운데 상태 줄 `고칠 선택`에 없는 ID를 PR 설명에 적는다.
   - 고치지 않기로 한 지적 가운데 이유가 "요구사항이 정하지 않았다"인 것은 5번의 "요구사항 수준의 미정"과 같이 G-n으로 올릴지 묻는다. 올리면 5번에서 함께 반영하고, 사용자가 올리지 않기로 하면 6번의 "반영하지 않음"에 그 지적과 "G-n으로 올리지 않음"을 적는다. "후속으로 정한다"만 쓰지 않는다.
   - 고친 뒤 테스트를 다시 실행한다.
5. "뒤 작업에 넘길 것"(reviewer가 보고한 것과, 메모 파일 `docs/specs/*/handoff/*.md`에 적힌 것)이나 4번에서 G-n으로 올리기로 한 지적이 있으면 스펙 문서 수정안으로 만들어 보여 주고, 승인받은 항목만 반영한다. PR 설명은 뒤 작업을 하는 세션이 읽지 못하므로 PR 설명에만 남기지 않는다. 메모 파일은 이 브랜치가 더한 것만 읽는다(`git diff origin/main...HEAD --name-only --diff-filter=A -- docs/specs`에서 `handoff/` 아래 파일. 로컬 `main`으로 비교하면 뒤처졌을 때 다른 PR이 머지한 메모가 섞인다). 없으면 reviewer가 보고한 것만 다룬다. `-review.md`를 재사용했으면 reviewer가 보고한 것은 그 파일 첫 절의 "뒤 작업에 넘길 것"에 뒤 절들의 "뒤 작업에 넘길 것 판정"을 절 순서대로 적용한 것이다(`무효`는 빼고 `바뀜`은 바뀐 문장으로). `main`에 이미 있는 메모 파일(다른 PR이 지우지 않고 머지한 것)은 반영하지 않고 경로만 알린다.
   - 메모 파일의 항목은 최종 코드(4번에서 고친 뒤)와 대조해, 여전히 유효하고 reviewer의 "뒤 작업에 넘길 것"과 같은 기준(아직 하지 않은 작업이 스펙만 읽고 구현하면 틀리게 되는 것. 컴파일 오류나 시그니처로 바로 드러나는 것은 제외)에 드는 것만 수정안에 넣는다. 뺀 항목은 이유와 함께 보여 준다. reviewer가 보고한 것과 같은 내용이면 하나로 합친다. 메모 파일은 수정안에 넣을 항목이 없거나 사용자가 모두 빼더라도 5번을 마칠 때 지운다(사용자가 뺀 항목은 6번의 "반영하지 않음"에 적는다. 기준에 들지 않아 거른 항목은 적지 않는다).
   - 작업 본문의 마지막 줄(`_Requirements: …_` 또는 `**Validates: …**`) 바로 앞에, 본문의 다른 항목과 같은 들여쓰기로 `- 주의(<넘긴 작업 번호> 리뷰): …` 또는 `- 미정(여기서 정함): …` 한 줄을 넣는다. 그런 줄이 없는 작업(Checkpoint 등)은 본문 끝에 넣는다. 번호는 이 PR의 작업 번호(브랜치 이름의 번호, PR 경계가 여러 하위 작업을 묶으면 범위. 예: `주의(2.1~2.3 리뷰)`)다. 본문에 같은 내용이 있으면 넣지 않는다.
   - 넣기 전에 대상 작업의 상태를 `/task`와 같은 기준으로 확인한다. `origin/main`의 체크박스로 이미 완료된 작업이면 본문에 넣지 않고, 머지된 구현이 그 항목과 어긋나는지 확인하라고 알린다. 이 PR이 끝낸 작업(이 브랜치에서 체크박스를 고친 작업)이 대상이면 본문에 넣지 않고, 그 구현이 항목과 맞는지만 확인한다. 다른 브랜치에서 진행 중인 작업(브랜치 이름에 `-<단계>-<번호>-` 또는 `/<단계>-<번호>-`)이면 본문에 넣되, 그 브랜치는 rebase 전까지 이 줄을 보지 못하므로 수정안과 PR 설명에 "진행 중: <브랜치>, 작성자에게 직접 알릴 것"을 적는다.
   - 작업 본문이 아닌 곳으로 가는 것: 설계 문서가 코드와 다르면 `design.md`의 그 절을 고친다. 실제 응답으로 확인해야 하는 가정은 그것을 확인하는 작업 본문에 더한다. 다른 스펙의 작업이면 그 스펙의 `tasks.md`에 넣고, 그 스펙의 작업 번호로 읽히지 않게 라벨에 단계를 붙인다(예: `주의(P1 2.3 리뷰)`). 요구사항 수준의 미정은 임의로 정하지 않고 설계의 "요구사항 공백"에 올릴지 묻는다. 올리기로 하면 `design.md`의 "요구사항 공백", 스펙 색인(`README.md`)의 결정 대기 표, `tasks.md` Notes의 "막는 작업" 표를 함께 고치고 제안값을 적는다(`/task`는 결정 대기를 색인과 Notes에서 읽는다).
   - 근거가 `스펙 추론`인 항목은 수정안에 그렇게 표시해 보여 준다. 사용자가 뺄 수 있어야 한다. 메모 파일의 항목은 구현하면서 확인한 것이므로 `코드 확인`으로 보되, 뒤 작업이 어떻게 구현될지에 대한 가정이 들어 있으면 `스펙 추론`으로 표시한다.
   - 반영한 문서 변경은 이 PR에 함께 넣는다. 커밋은 사용자가 한다(코드와 나눠 `docs:` 커밋으로 하고, 메모 파일 삭제를 그 커밋에 넣어야 `main`에 남지 않는다고 안내한다).
   - 넘길 것이 없어도 항상, 마지막에 이 브랜치의 `/task-flow` 파일(3번에서 정한 `<스펙>`의 handoff 폴더에 있는 `<번호>-plan.md`, `<번호>-review.md`, `<번호>-context-review.md`)을 로컬에서 지운다(커밋되지 않는 파일이라 커밋할 것은 없다). 4번과 이 5번에서 다 읽은 뒤에 지운다.
6. `.github/pull_request_template.md` 형식으로 PR 설명 초안을 출력한다. 검증 증거(실행한 명령과 결과 요약)를 포함한다. 템플릿의 "뒤 작업에 넘긴 것"에 5번에서 반영한 것은 작업 번호와 한 줄 요약을 적고, 반영하지 않기로 한 항목은 내용을 적는다. 넘긴 항목은 "AI 리뷰 지적 n건"에 세지 않는다. 5번에서 다른 작업의 설계(`design.md`)를 고쳤거나 결정 대기 항목(G-n)을 더했으면 "기능 리드 승인 필요"를 적는다(주의·미정 줄만 더했거나, 설계 문서를 이 PR의 코드나 이미 머지된 코드에 맞춰 정정한 것뿐이면 적지 않는다. `docs/product/PLAYBOOK.md` "승인 규칙 요약").
7. push나 PR 생성은 하지 않는다. 사용자가 직접 확인하고 올린다.

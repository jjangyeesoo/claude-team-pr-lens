현재 브랜치를 PR 전에 점검한다.

1. `git status`, `git diff main...HEAD --stat`으로 변경 범위를 확인한다.
   - 커밋하지 않은 변경이 있으면 먼저 알리고 멈춘다. reviewer는 `git diff main...HEAD`로 커밋된 변경만 본다.
   - PR 단위는 `tasks.md`의 상위 작업 하나다. 그 작업에 "PR 경계"가 적혀 있으면 이 브랜치가 경계 하나에 해당하는지 확인한다.
   - 크기는 `src/main` 변경만 센다(테스트, 픽스처, 문서 제외). 400줄을 넘으면 `tasks.md`의 PR 경계로 나눌 수 있는지 먼저 보고, 나눌 수 없으면 PR 설명에 넣을 이유를 한 줄 제안한다.
2. 바뀐 스택만 검증하고 결과(통과 수, 실패 여부)를 증거로 기록한다.
   - `backend/`가 바뀌었으면 `backend/`에서 `./gradlew spotlessApply test`
   - `web/`이 바뀌었으면 `web/`에서 `npm run verify`와 `npm run build`
   - backend 응답 DTO가 바뀌었는데 `web/src/lib/api/types.ts`가 그대로면 짚어 준다
3. 바뀐 경로에 따라 서브에이전트로 diff를 리뷰한다.
   - `.claude/`나 `CLAUDE.md`(하위 폴더의 것 포함)가 바뀌었으면 `context-reviewer`로 리뷰한다. 함께 바뀐 `docs/`, `.github/`, 루트 `README.md`도 `context-reviewer`가 본다.
   - `backend/`나 `web/`이 바뀌었으면 `reviewer`로 리뷰한다. 관련 스펙이 있으면 스펙 폴더 경로(`docs/specs/<이름>/`)와 작업 번호를 함께 넘긴다. `.claude/hooks/`의 Java 파일이 바뀌었으면 `reviewer`에게도 넘긴다.
   - 둘 다 해당하면 둘 다 실행한다. 어느 쪽에도 해당하지 않으면(문서만 바뀐 브랜치) `reviewer`만 쓴다.
4. 리뷰 결과를 "반드시 수정", "선택", "뒤 작업에 넘길 것"으로 나눠 보여 주고(`context-reviewer`는 앞의 두 그룹만 보고한다), "반드시 수정"만 고친다. 고친 뒤 테스트를 다시 실행한다.
5. "뒤 작업에 넘길 것"(reviewer가 보고한 것과, 이 세션에서 `/task`가 마무리할 때 보고한 것)이 있으면 스펙 문서 수정안으로 만들어 보여 주고, 승인받은 항목만 반영한다. PR 설명은 뒤 작업을 하는 세션이 읽지 못하므로 PR 설명에만 남기지 않는다. 이 세션에 `/task`의 마무리 보고가 남아 있지 않으면(세션을 새로 시작했거나 압축된 경우) `/task`가 보고한 넘길 항목이 있었는지 사용자에게 묻는다.
   - 작업 본문의 마지막 줄(`_Requirements: …_` 또는 `**Validates: …**`) 바로 앞에, 본문의 다른 항목과 같은 들여쓰기로 `- 주의(<넘긴 작업 번호> 리뷰): …` 또는 `- 미정(여기서 정함): …` 한 줄을 넣는다. 그런 줄이 없는 작업(Checkpoint 등)은 본문 끝에 넣는다. 번호는 이 PR의 작업 번호(브랜치 이름의 번호, PR 경계가 여러 하위 작업을 묶으면 범위. 예: `주의(2.1~2.3 리뷰)`)다. 본문에 같은 내용이 있으면 넣지 않는다.
   - 넣기 전에 대상 작업의 상태를 `/task`와 같은 기준으로 확인한다. `origin/main`의 체크박스로 이미 완료된 작업이면 본문에 넣지 않고, 머지된 구현이 그 항목과 어긋나는지 확인하라고 알린다. 다른 브랜치에서 진행 중인 작업(브랜치 이름에 `-<단계>-<번호>-`)이면 본문에 넣되, 그 브랜치는 rebase 전까지 이 줄을 보지 못하므로 수정안과 PR 설명에 "진행 중: <브랜치>, 작성자에게 직접 알릴 것"을 적는다.
   - 작업 본문이 아닌 곳으로 가는 것: 설계 문서가 코드와 다르면 `design.md`의 그 절을 고친다. 실제 응답으로 확인해야 하는 가정은 그것을 확인하는 작업 본문에 더한다. 다른 스펙의 작업이면 그 스펙의 `tasks.md`에 넣고, 그 스펙의 작업 번호로 읽히지 않게 라벨에 단계를 붙인다(예: `주의(P1 2.3 리뷰)`). 요구사항 수준의 미정은 임의로 정하지 않고 설계의 "요구사항 공백"에 올릴지 묻는다. 올리기로 하면 `design.md`의 "요구사항 공백", 스펙 색인(`README.md`)의 결정 대기 표, `tasks.md` Notes의 "막는 작업" 표를 함께 고치고 제안값을 적는다(`/task`는 결정 대기를 색인과 Notes에서 읽는다).
   - 근거가 `스펙 추론`인 항목은 수정안에 그렇게 표시해 보여 준다. 사용자가 뺄 수 있어야 한다. `/task`가 보고한 항목은 구현하면서 확인한 것이므로 `코드 확인`으로 보되, 뒤 작업이 어떻게 구현될지에 대한 가정이 들어 있으면 `스펙 추론`으로 표시한다.
   - 반영한 문서 변경은 이 PR에 함께 넣는다. 커밋은 사용자가 한다(코드와 나눠 `docs:` 커밋으로 하라고 안내한다).
6. `.github/pull_request_template.md` 형식으로 PR 설명 초안을 출력한다. 검증 증거(실행한 명령과 결과 요약)를 포함한다. 템플릿의 "뒤 작업에 넘긴 것"에 5번에서 반영한 것은 작업 번호만 적고, 반영하지 않기로 한 항목은 내용을 적는다. 넘긴 항목은 "AI 리뷰 지적 n건"에 세지 않는다. 5번에서 다른 작업의 설계(`design.md`)를 고쳤거나 결정 대기 항목(G-n)을 더했으면 "기능 리드 승인 필요"를 적는다(주의·미정 줄만 더했거나, 설계 문서를 이 PR의 코드나 이미 머지된 코드에 맞춰 정정한 것뿐이면 적지 않는다. `docs/product/PLAYBOOK.md` "승인 규칙 요약").
7. push나 PR 생성은 하지 않는다. 사용자가 직접 확인하고 올린다.

대상: $ARGUMENTS (첫 값은 `docs/specs/` 아래 스펙 폴더 이름, 둘째 값은 `tasks.md`의 작업 번호. 예: `pr-lens-p1-cli 7.3`)

스펙 폴더나 `tasks.md`가 없으면 `docs/specs/README.md`의 스펙 목록을 보여 주고 멈춘다. 스펙 파일은 크므로 통째로 읽지 않는다.

너는 매니저다. 계획, 구현, 리뷰는 에이전트에게 맡기고, 너는 상태 줄, 브랜치, 사람 게이트(G1 브랜치, G2 계획, G3 최종 보고), 결과 취합만 한다. **계획 파일 본문(9번의 `## G3 검증` 절은 빼고), 구현 파일, 테스트는 직접 고치지 않는다.** implementer가 도는 동안 사용자가 말을 걸어도 구현 파일을 고치거나 검증 명령을 돌리지 않는다. implementer가 끝나면 완료 알림이 오므로 기다린다. 네가 턴을 끝낼 때 메인 Stop hook 검증이 실패하면(implementer가 남긴 빨간 트리) 고치지 않는다. 실패 내용을 알리고, 새 implementer로 그 슬라이스를 다시 할지 묻는다.

## 파일과 표기
- 계획 파일: `docs/specs/<스펙>/handoff/<번호>-plan.md`. `<번호>`는 브랜치 이름의 번호(PR 경계의 첫 하위 작업 번호)다. 리뷰 파일: 같은 폴더의 `<번호>-review.md`(reviewer), `<번호>-context-review.md`(context-reviewer). 셋 다 gitignore되어 커밋되지 않고, `/pr-ready`가 지운다. 메모 파일 `<번호>.md`는 implementer가 커밋한다.
- 리뷰 ID: 파일에는 리뷰어가 쓴 ID(`M1`, `S1`)를 그대로 두고, 그 밖(상태 줄, implementer 전달, 보고)에서는 파일로 머리글자를 붙인다. `-review.md`는 `R-`, `-context-review.md`는 `C-`(예: `R-M1`, `C-S2`).
- 리뷰 파일은 덮어쓰지 않고 리뷰마다 `## 리뷰 N (SHA <리뷰한 브랜치 끝 SHA>, 첫|확인)` 절 아래에 리뷰어 보고를 그대로 이어 쓴다. 리뷰 횟수는 절 수다.
- 검증 확인: `java -Dfile.encoding=UTF-8 .claude/hooks/VerifyOnStop.java --check <implementer agentId>`. 출력이 `ok:`이고 exit 0이면 통과다. 아니면 "결과 없음"으로 보고 이유를 보여 준다(종료 검증 결과 파일 `build/claude-verify/implementer-result.json`이 그 implementer의 것이 아니거나, 스택 결과가 `pass`·`pass-nothing-to-verify`가 아니거나, implementer가 끝난 뒤 내용이 바뀌었거나, 끝날 때 트리가 깨끗하지 않았음). 대체 검증: `--verify <agentId>`. implementer가 `SubagentHandback` 도구를 부르지 않고 일반 응답으로 끝나면 종료 검증 hook이 돌지 않아 결과 파일이 없거나 이전 implementer의 것이다. 이때 한 번 돌려 같은 검증을 하고 `--check`와 같이 판정한다(실패하면 `failed` 표시를 남김). 이 명령과 `--check`, 아래 `--mark`·`--unmark`는 저장소 루트에서 실행한다(`cd "$(git rev-parse --show-toplevel)"`). 다른 폴더에서 실행하면 그 폴더의 `build/claude-verify/`를 본다.

### 상태 줄
계획 파일 맨 위, 빈 줄 전까지다. **너만 고친다.** 상태가 바뀔 때마다 고친다.
```
상태: 계획 중
브랜치: feat/t2-p1-7.2-pr-fetcher
승인: 없음
planner: 없음 · implementer: 없음
슬라이스: 없음
실패 테스트: 없음
고칠 선택: 없음
남긴 반드시 수정: 없음
```
- `승인`: G2를 통과하면 `G2 <날짜>`, 재승인하면 ` · 재승인 <날짜>`를 더한다
- `planner`·`implementer`: 에이전트를 띄우거나 `SendMessage`로 재개할 때마다 그 agentId로 고친다. agentId는 같은 세션에서만 쓴다. `/clear`나 새 세션 뒤에는 새 에이전트를 띄운다
- `슬라이스`: 지금 구현 중이거나 마지막으로 끝낸 슬라이스(`2/3 (7.4+7.5)`)
- `실패 테스트`: 슬라이스마다 `<슬라이스 첫 하위 작업 번호>=<값>`을 쉼표로 잇는다. 값은 확인한 `test:` 커밋 SHA, 테스트 목록이 `없음`이거나 아직이면 `없음`, 테스트만 쓰는 슬라이스는 `해당 없음(<그 슬라이스 첫 커밋 SHA>)`
- `고칠 선택`: 첫 리뷰 뒤 사용자가 고르라고 한 "선택" ID(`R-S1, C-S2`). 묻고 기다리는 동안 `묻는 중`, 고르지 않았거나 "선택"이 없으면 `없음`
- `남긴 반드시 수정`: "수정 필요"에서 사용자가 그대로 두라고 한 ID. 그 밖에는 `없음`

## 1. 상태 확인 (항상 먼저)
1. `origin`이 있으면 `git fetch --prune origin`을 실행한다. 없으면 건너뛰고 "원격이 없어 다른 사람의 진행 상황은 알 수 없다"고 알린다. 아래 `origin/main`은 원격이 없으면 로컬 `main`으로 읽는다.
2. **완료**: `origin/main`의 체크박스로 판단한다(`git grep -n -E "^\s*- \[[ x]\]" origin/main -- docs/specs/<스펙>/tasks.md`).
3. **진행 중**: 원격과 로컬 브랜치 가운데 이름에 `-<단계>-<번호>-` 또는 `/<단계>-<번호>-`가 들어 있는 것(예: `feat/t2-p1-5-diff-parser`는 P1 작업 5 전체, `feat/shared-p1-2.1-model-types`는 2.1이 속한 PR 경계, `chore/p2-28-context`는 P2 컨텍스트 작업 28). 브랜치 이름, 마지막 커밋의 작성자와 날짜를 함께 본다. push하지 않은 다른 사람의 작업은 보이지 않는다.
4. **선행 작업**은 `tasks.md`의 Overview(선머지 범위, 트랙 사이 의존), 작업 본문, Task Dependency Graph로 판단한다. wave는 순서 안내이지 전부가 의존은 아니다. 막는 것으로 보는 것은 선머지 작업, 같은 상위 작업 안에서 앞 wave에 있는 하위 작업, Overview나 본문이 이름을 적은 작업이다. 그 밖에 앞 wave의 미완료 작업은 "확인 필요"로만 알린다.

## 2. 작업 번호가 없을 때
스펙 색인(`README.md`)의 트랙 표를 기준으로 트랙별 목록을 보여 주고 끝낸다. 진행하지 않는다. 목록은 PR 경계 단위로 묶는다(이 skill이 경계 단위로 진행하므로). 완료는 말단 작업 수로 센다.
- 시작 가능: 선행 작업이 완료됐고 진행 중이 아닌 것. `*` 작업과 결정 대기(Notes의 "막는 작업" 표)에 걸린 작업은 표시해 둔다
- 진행 중: 브랜치 이름, 작성자, 날짜
- 막힘: 기다리는 작업 번호
- 완료는 개수만 적는다

## 3. 작업 번호가 있을 때: 대상과 재개 판단
1. 색인, `tasks.md`의 Overview와 Notes, 받은 번호의 본문을 읽는다. 받은 번호가 속한 **PR 경계 전체**가 대상이다(상위 작업 번호를 받으면 첫 PR 경계, 경계 안의 번호(`7.3`)를 받으면 그 경계(`7.2~7.5`)). 경계 표시가 없는 상위 작업은 상위 작업 전체가 경계다. 경계의 첫 하위 작업 번호가 `<번호>`다.
2. 계획 파일이 있으면 상태 줄을 읽고 아래 "상태와 재개"의 그 상태 행을 따른다. G1은 건너뛴다. 상태가 "계획 중"이 아니면 체크아웃한 브랜치가 상태 줄 `브랜치:`와 같은지 먼저 본다. 다르면 알리고 멈춘다(`git switch <브랜치>`를 제안한다). 상태 줄의 "교차 확인"이 산출물(체크아웃한 브랜치, 커밋, 리뷰 파일)과 어긋나면 **알리고 멈춘다**. 상태 줄은 사용자가 확인한 뒤에 고친다.
3. 계획 파일은 없고 이 작업의 브랜치가 있으면, 브랜치마다 `git log -1 --format=%an origin/main..<브랜치>`(브랜치에만 있는 마지막 커밋의 작성자)를 `git config user.name`과 비교한다. 결과가 비어 있으면(만들자마자 push해 작업 커밋이 아직 없음) 누구의 것인지 알 수 없으므로 다른 사람의 브랜치로 본다. 다른 사람의 브랜치만 있으면 4번으로 간다(G1에서 알리고 계속할지 묻는다). 내 브랜치가 있으면 `/pr-ready`를 이미 돌렸거나 다른 PC에서 시작한 작업이다. 브랜치의 커밋과 PR 여부(`gh pr list --head <브랜치>`)를 알리고 멈춘다. 어떻게 이어 갈지는 사용자가 정한다.
4. 둘 다 없으면 4번부터 시작한다.

## 4. 시작해도 되는지 확인하고 G1
1. 경계 안 하위 작업이 모두 `origin/main`에서 완료면 멈춘다. 선행 작업이 끝나지 않았으면 무엇을 기다리는지 알리고 멈춘다.
2. 작업 종류별로 나눈다. 경계 전체가 "사람이 수행"이면 할 일 목록만 보여 주고 멈춘다. Checkpoint 작업이면 이 skill을 쓰지 않고 `/task`로 하라고 알린다(코드를 쓰지 않으므로 단계를 나눌 것이 없다).
3. 결정 대기(D-n, G-n)에 걸린 하위 작업이 있으면 색인에 적힌 대로(제안값 또는 요구사항 문구. 색인이 "제안값으로 대신할 수 없다"고 한 항목이면 멈춘다) 진행한다고 알린다(임의로 확정하지 않는다).
4. **G1**: 다른 사람의 브랜치가 진행 중이면(아래 "게이트 조건" G1) 알리고 계속할지 묻는다. 브랜치 이름을 제안하고 **멈춘다**. 형식은 `feat/<track>-<단계>-<번호>-<slug>`(루트 `CLAUDE.md`), `.claude/`나 `CLAUDE.md`를 고치는 컨텍스트 작업(색인 트랙 표의 "컨텍스트")은 `chore/<단계>-<번호>-<slug>`다. 지금 브랜치가 이미 이 작업의 브랜치면 그대로 쓴다고 알리고 확인받는다. 다른 작업의 브랜치이거나 커밋하지 않은 변경이 있으면 함께 알린다.
5. 확인받으면 `origin/main`에서 브랜치를 만들고(`worktree-<이름>` 브랜치면 `git branch -m`), 원격이 있으면 `git push -u origin <브랜치>`로 올린다. 그 뒤 위 "상태 줄" 형식으로 상태 줄만 있는 계획 파일 골격을 만든다(`상태: 계획 중`, `브랜치:`에 이름, 나머지는 `없음`).

## 5. 계획과 G2
1. planner를 부른다. 넘기는 것: 스펙 폴더, PR 경계(예: `7.2~7.5`), 브랜치, 계획 파일 경로. 반환된 agentId를 상태 줄 `planner:`에 적는다. 완료 알림을 기다린다.
2. 계획 파일을 읽어 요약을 보여 준다: 슬라이스 목록과 순서, 슬라이스별 테스트 목록(테스트 이름과 인수 기준), 만들고 고칠 파일, "결정", "주의·미정 대응", `실패 테스트: 해당 없음`인 슬라이스(따로 표시), "요구사항 변경", "질문" 절 전체. 그리고 G2 게이트 조건을 계산해 "자동이었다면 멈췄을 이유"로 보여 준다(없으면 `없음`).
3. **G2에서 멈춘다.** 질문의 답과 수정 요청은 같은 세션이면 `SendMessage`(상태 줄의 planner agentId)로, `/clear`나 새 세션 뒤면 새 planner에게 계획 파일 경로와 피드백만 넘겨 고치게 한다. 너는 계획을 직접 고치지 않는다. 고친 뒤 2번부터 다시 한다.
4. 승인받으면 상태 줄을 `상태: 계획 승인`, `승인: G2 <날짜>`로 고치고 6번으로 간다.

## 6. 구현 (슬라이스마다)
슬라이스를 계획 순서대로 하나씩 한다.
1. 상태 줄을 `상태: 구현 중`, `슬라이스: N/전체 (<하위 작업>)`로 고친다.
2. 새 implementer를 부른다. 넘기는 것: 계획 파일 경로, "`## 공통`과 `## 슬라이스 N (…)` 절만 읽는다", 브랜치. 반환된 agentId를 상태 줄 `implementer:`에 적는다. 턴을 끝내고 완료 알림을 기다린다. implementer가 도는 동안 메인 Stop hook은 검증을 건너뛰고 그렇다고 알린다(정상).
3. 보고가 `BLOCKED:`로 시작하면 그 질문을 사용자에게 묻는다. 답을 `SendMessage`로 그 implementer에게 보내고(재개하면 메인 Stop 입력의 `background_tasks`로 실행 중으로 보이고, 남은 `blocked` 표시는 다음 보고 때 hook이 정리한다) 상태 줄 `implementer:`를 확인한 뒤 2번처럼 기다린다. 답을 기다리는 동안 트리는 빨간 채이고, 메인 Stop은 `blocked` 표시를 보고 검증을 건너뛴다. `--check`가 결과 파일이 없거나 `agent_id`가 다르다고 하면 hook이 돌지 않은 것이므로(`SubagentHandback` 없이 끝남), 턴을 끝내기 전에 `--mark <agentId> blocked`로 표시를 쓴다.
4. 완료 보고가 오면 검증 확인(`--check <agentId>`)을 돌린다. 결과 파일이 없거나 `agent_id`가 다르다는 이유뿐이면 종료 검증이 돌지 않은 것이므로, 새 implementer를 띄우지 않고 `--verify <agentId>`를 한 번 돌려 그 출력을 검증 확인으로 쓴다(implementer가 끝난 뒤라 매니저가 돌린다. 그 implementer의 다음 보고부터는 hook이 돈다). 통과가 아니면 다음 슬라이스로 넘어가지 않고 이유를 보여 주고 사용자에게 묻는다(게이트 "슬라이스 사이"). 고를 수 있는 것: 새 implementer로 같은 슬라이스를 다시 하기(상태 "구현 중"의 재개와 같음), 그대로 다음으로 가기(G3에서 멈춤), 중단(`--unmark`). 종료 검증이 두 번 실패해 풀려났으면 `failed` 표시가 남아, 다시 하지 않는 동안 메인 Stop이 검증을 건너뛴다는 것도 알린다(사용자가 메인에서 직접 고치려면 `--unmark` 뒤에).
5. 실패 테스트 커밋을 확인해 상태 줄 `실패 테스트:`에 적는다. 이 슬라이스의 커밋은 `git log --reverse --format="%H %s" origin/main..HEAD`에서 상태 줄에 이미 적힌 앞 슬라이스 커밋들 다음의 커밋이다.
   - 테스트 목록이 있는 슬라이스: 보고된 SHA가 이 슬라이스의 첫 커밋이고, 제목이 `test:`로 시작하고, `git diff --name-only <SHA>^ <SHA>`의 파일이 테스트(`*/src/test/*`, `*.test.ts`, `*.test.tsx`)이거나 그 슬라이스 "테스트 목록"의 `스텁` 열에 있는 것뿐이면 SHA를 적는다. 아니면 적지 않고(`없음`) G3에서 멈출 것이라고 알린다.
   - `실패 테스트: 해당 없음`인 슬라이스: `해당 없음(<첫 커밋 SHA>)`. 테스트 목록이 `없음`이면 `없음`.
6. 보고의 `다음 슬라이스 영향:`이 `없음`이 아니면 "계획 재승인": 상태 줄을 `상태: 계획 재승인`으로 고치고, 같은 planner에게(새 세션이면 새 planner) 보고 내용을 넘겨 다음 슬라이스 절만 고치게 한다. 고친 슬라이스 절에 G2 기계 조건(슬라이스 분할, 테스트 대응, 주의·미정 대응)을 다시 계산해 보여 주고 승인을 묻는다. 승인받으면 `승인`에 ` · 재승인 <날짜>`를 더한다.
7. 다음 슬라이스로 1번부터 반복한다. 마지막 슬라이스가 끝나면 7번으로 간다.

## 7. 리뷰
1. 상태 줄을 `상태: 리뷰 중`으로 고친다. `git fetch origin`을 실행한다(리뷰어는 fetch하지 않는다).
2. 부를 리뷰어를 바뀐 경로(`git diff --name-only origin/main...HEAD`)로 고른다(`/pr-ready` 3번과 같은 규칙):
   - `.claude/`나 `CLAUDE.md`(하위 폴더 포함)가 바뀌었으면 `context-reviewer`
   - `backend/`나 `web/`, `.claude/hooks/`의 Java 파일이 바뀌었으면 `reviewer`
   - 둘 다 해당하면 둘 다, 어느 쪽도 아니면 `reviewer`만
3. **첫 리뷰**를 부른다(둘이면 함께 띄운다).
   - `reviewer`: 스펙 폴더, 작업 번호로 경계 범위(예: `7.2~7.5`. 경계 안 다른 하위 작업을 범위 밖으로 보지 않게), 브랜치, 계획 파일 경로, 슬라이스별 실패 테스트 SHA(상태 줄 값)
   - `context-reviewer`: 브랜치, "바뀐 skill·agent를 실행한 결과 없음"
4. 첫 리뷰 결과에 "선택" 행이 있으면 **리뷰 파일보다 먼저** 상태 줄을 `고칠 선택: 묻는 중`으로 고친다(둘 사이에서 끊겨도 재개 때 다시 묻도록). 그 뒤 리뷰어마다 리뷰 파일에 `## 리뷰 1 (SHA <git rev-parse HEAD>, 첫)` 절로 저장한다.
5. "반드시 수정"과 "선택"을 머리글자 붙은 ID로 보여 준다. "선택" 표(추천, 수정안, 이유 포함)를 보여 주고 고칠 ID를 묻는다(없으면 묻지 않는다). 답을 `고칠 선택`에 적는다(고르지 않으면 `없음`). "뒤 작업에 넘길 것"은 보여 주기만 한다(`/pr-ready`가 반영한다).
6. 모든 리뷰어의 "반드시 수정"이 없고 `고칠 선택`이 `없음`이면 9번(G3)으로 간다. 아니면 8번으로 간다.

## 8. 수정과 확인 리뷰
1. 상태 줄을 `상태: 수정 중`으로 고친다. 넘길 ID는 리뷰 파일마다 마지막 절 "반드시 수정"의 ID에서 `남긴 반드시 수정`에 있는 것을 뺀 것이다. 그 리뷰 파일에 아직 확인 리뷰 절이 없으면(첫 수정) `고칠 선택` 가운데 그 파일 머리글자의 ID도 넘긴다. 두 번째 수정부터는 `고칠 선택`을 넘기지 않는다(확인 리뷰에서 이미 판정됨). `고칠 선택` 값은 `/pr-ready`가 쓰므로 지우지 않는다. 모두 머리글자를 붙여 넘긴다.
2. implementer를 수정 모드로 부른다. 같은 세션이면 마지막 슬라이스의 implementer에게 `SendMessage`, 아니면 새 implementer. 넘기는 것: 계획 파일 경로, 리뷰 파일 경로, 고칠 ID 목록, "수정 모드, 경계 전체". 상태 줄 `implementer:`를 고치고 기다린다. `BLOCKED:`면 6번 3과 같이 한다.
3. 완료 보고가 오면 검증 확인(`--check`, 종료 검증이 돌지 않았으면 `--verify`)을 6번 4와 같이 돌린다. 통과가 아니면 6번 4와 같이 이유를 보여 주고 묻는다.
4. 상태 줄을 `상태: 리뷰 중`으로 고치고 `git fetch origin` 뒤, **첫 리뷰를 돌린 리뷰어 모두에게** 확인 리뷰를 부른다(지적이 없던 쪽도. 수정이 그 영역을 건드렸을 수 있고, 리뷰 파일 SHA를 `HEAD`에 맞춰야 `/pr-ready`가 재사용하므로). 확인 리뷰 모드로 넘기는 것:
   - 그 리뷰어의 리뷰 파일 경로(앞 리뷰의 ID, 판정, 리뷰한 SHA)
   - 그 리뷰 파일의 마지막 절이 첫 리뷰일 때만: `고칠 선택` 가운데 그 리뷰어 머리글자의 ID를 머리글자를 떼어서(`R-S1` → reviewer에 `S1`)
   - `reviewer`에는 "뒤 작업에 넘길 것" 목록: 첫 절의 항목에 앞선 확인 리뷰 절들의 "뒤 작업에 넘길 것 판정"을 절 순서대로 적용한 것(`무효`는 빼고 `바뀜`은 바뀐 문장으로)
5. 결과를 각 리뷰 파일에 `## 리뷰 N (SHA <HEAD>, 확인)` 절로 이어 쓴다. 확인 리뷰는 새 "선택"을 내지 않으므로 다시 묻지 않는다. `남긴 반드시 수정`의 ID 가운데 이번 절 "앞 리뷰 판정"이 `해결됨`인 것은 `남긴 반드시 수정`에서 뺀다(다른 수정으로 함께 해결된 경우. "PR 준비" 교차 확인과 G3 보고가 어긋나지 않게).
6. 어느 리뷰 파일이든 마지막 절 "반드시 수정" 표에 `남긴 반드시 수정`에 없는 행이 있으면 "수정 필요"(아래 표), 없으면 9번(G3)으로 간다.

## 9. G3 최종 보고
상태 줄을 `상태: PR 준비`로 고치고(그 전에 아래 조건을 계산한다) 보고한다. PR은 만들지 않고 `/pr-ready`를 안내한다.
- 슬라이스별: 대응시킨 인수 기준과 테스트, 실패 테스트 커밋, 승인받은 계획과 달라진 점, 설계와 달라진 점, `test:` 커밋 뒤 테스트 변경과 이유(implementer 보고에서)
- 색인대로 구현한 결정 대기 항목, 정리한 "주의"·"미정"(계획 파일 "주의·미정 대응" 표를 체크리스트로), 메모 파일에 적은 항목
- 리뷰 요약: 리뷰어별 리뷰 횟수, 해결한 ID, 남긴 반드시 수정과 그 이유, 고치지 않은 "선택", `diff 밖` 항목
- 검증 증거: 마지막 implementer의 `--check` 출력(스택별 결과). 그 출력과 `git rev-parse HEAD`를 계획 파일 끝의 `## G3 검증` 절에 남긴다(있으면 고친다). `/clear` 뒤에는 implementer 결과 파일로 다시 확인할 수 없으므로 재개한 G3는 이 절을 쓴다
- G3 게이트 조건 결과("자동이었다면 멈췄을 이유", 없으면 `없음`)
- 다음에 할 작업

## 상태와 재개
`/task-flow <스펙> <번호>`를 다시 실행했을 때 계획 파일의 `상태:`로 이어 간다.

| 상태 | 교차 확인 | 재개 시 할 일 |
|---|---|---|
| 계획 중 | `승인: 없음` | 계획 본문(`## 공통`)이 있으면 5번 2부터. 없으면 planner를 다시 부른다(5번 1) |
| 계획 승인 | `승인`에 날짜가 있음 | 6번(첫 슬라이스) |
| 구현 중 | 체크아웃한 브랜치가 상태 줄의 브랜치 | 상태 줄 `슬라이스`부터 이어 간다. `git status`, `origin/main..HEAD`의 커밋, 실패하는 테스트 목록(그 슬라이스 테스트만 돌려 확인)을 모아 계획 파일과 함께 새 implementer에게 넘긴다. `origin/main..HEAD`에 상태 줄에 없는 `test:` 커밋이 있으면(죽은 implementer가 남긴 것) 6번 5의 기준으로 확인해 그 슬라이스 값으로 적고 새 implementer에게 알린다(같은 커밋을 다시 만들지 않게). 전에 `BLOCKED`였으면 그 질문을 다시 묻는다. 트리가 빨간 채로 질문을 기다리면, 턴을 끝내기 전에 `java -Dfile.encoding=UTF-8 .claude/hooks/VerifyOnStop.java --mark <이전 implementer agentId>`로 표시를 다시 쓴다(`/clear`나 새 세션 뒤에는 세션이 달라 이전 표시가 무효다. 쓰지 않으면 메인 Stop이 빨간 트리를 검증한다) |
| 계획 재승인 | 작업 트리가 깨끗함 | 공통 절 "수정 이력"에 이번 수정이 없으면 planner를 다시 부른다. 있으면 6번 6의 확인과 승인부터 |
| 리뷰 중 | 작업 트리가 깨끗하고 브랜치가 `origin/main`보다 앞섬 | 부를 리뷰어(7번 2)마다 리뷰 파일로 판단한다. 파일이 없으면 첫 리뷰(7번 3), 마지막 절 SHA가 `HEAD`와 다르면 확인 리뷰(8번 4). 모든 리뷰 파일의 마지막 절 SHA가 `HEAD`와 같으면: 첫 리뷰뿐이고 `고칠 선택: 묻는 중`이면 7번 5, "반드시 수정"이 있거나 `고칠 선택`이 `없음`이 아니면 8번, 둘 다 아니면 9번. 확인 리뷰 뒤면 8번 6 |
| 수정 중 | 체크아웃한 브랜치가 상태 줄의 브랜치 | 트리 상태와 커밋을 모아 새 implementer를 수정 모드로 띄운다(8번 2. 빨간 트리로 질문을 기다리면 `--mark`도 "구현 중"과 같이) |
| 수정 필요 | 리뷰 파일들의 마지막 절 SHA가 `HEAD`와 같고, 어느 한 파일의 마지막 절 "반드시 수정" 표에 `남긴 반드시 수정`에 없는 행이 있음 | 남은 항목을 보여 주고 ID마다 고칠지 그대로 둘지 묻는다. 그대로 둘 ID는 `남긴 반드시 수정`에 더한다. 고칠 ID가 있으면 8번 1부터(고친 뒤에는 늘 확인 리뷰를 한 번 더 한다), 없으면 9번으로 간다. 어느 리뷰 파일의 절이 이미 3개면 고치기를 제안하지 않고 그대로 두기나 중단만 묻는다(리뷰는 리뷰어마다 최대 3회) |
| PR 준비 | 7번 2로 고른 리뷰어마다 리뷰 파일이 있고, 리뷰 파일마다 마지막 절 "반드시 수정" 표의 ID에 머리글자를 붙인 집합이 `남긴 반드시 수정`과 같음 | G3 보고를 다시 보여 주고 `/pr-ready`를 안내한다. 검증 증거는 `## G3 검증` 절의 기록이다(그 절의 SHA가 `HEAD`와 다르거나 절이 없으면 그렇다고 알린다) |

사용자가 작업을 중단하기로 하면 `java -Dfile.encoding=UTF-8 .claude/hooks/VerifyOnStop.java --unmark`로 표시를 지우고(트리가 빨가면 다음 턴 끝에 메인 Stop이 한 번 막는다), push한 브랜치와 계획 파일이 남아 있다고 알린다(지울지는 사용자가 정한다).

## 게이트 조건
이번 버전은 모든 게이트에서 멈춘다. 아래 조건은 G2·G3 보고에 "자동이었다면 멈췄을 이유"로만 출력한다(다음 버전의 `--auto`가 쓴다). 슬라이스 사이의 두 조건은 지금도 멈춘다.

| 게이트 | 멈추는 조건 | 확인 방법 |
|---|---|---|
| G1 | 같은 `-<단계>-<번호>-` 또는 `/<단계>-<번호>-` 패턴의 다른 브랜치가 원격이나 로컬에 있음 | `git fetch --prune origin` 뒤 `git branch -a`. 3번 3에서 내 브랜치로 판정한 것만 제외한다(4번에 왔다면 대개 없음. 작업 커밋이 없는 내 브랜치는 여기서 묻고, 사용자가 그대로 쓴다고 하면 씀) |
| G2 | 결정 대기(D-n, G-n)에 걸림 | `tasks.md` Notes "막는 작업" 표에서 항목이 확정되지 않은 행에 경계 안 하위 작업 번호가 있음. 확정은 항목에 `확정`이 있거나, 그 행이 링크한 ADR이 `docs/adr/README.md`에 대체되지 않은 결정으로 올라 있음. Notes에 "막는 작업" 표가 없는 스펙이면 "판정할 수 없음(Notes에 '막는 작업' 표 없음)"으로 출력하고, 결정 대기는 색인과 작업 본문으로 확인함(4번 3) |
| G2 | 선행 spike가 끝나지 않음 | 작업 본문의 `막는 작업:` 줄에 경계 안 하위 작업 번호가 있고, 그 줄이 속한 작업이 `origin/main`에서 아직 `- [ ]` |
| G2 | 요구사항 변경을 제안함 | 계획 파일 "요구사항 변경" 절이 `없음`이 아님 |

대상: $ARGUMENTS (첫 값은 `docs/specs/` 아래 스펙 폴더 이름, 둘째 값은 `tasks.md`의 작업 번호. 예: `pr-lens-p1-cli 5.1`)

스펙 폴더나 `tasks.md`가 없으면 `docs/specs/README.md`의 스펙 목록을 보여 주고 멈춘다. 스펙 파일은 크므로 통째로 읽지 않는다.

## 1. 상태 확인 (항상 먼저)
1. `origin`이 있으면 `git fetch --prune origin`을 실행한다. 없으면 건너뛰고 "원격이 없어 다른 사람의 진행 상황은 알 수 없다"고 알린다.
2. **완료**: `origin/main`의 체크박스로 판단한다(`git grep -n -E "^\s*- \[[ x]\]" origin/main -- docs/specs/<스펙>/tasks.md`). 원격이 없으면 로컬 `main`을 본다.
3. **진행 중**: 원격과 로컬 브랜치 가운데 이름에 `-<단계>-<번호>-` 또는 `/<단계>-<번호>-`가 들어 있는 것(예: `feat/t2-p1-5-diff-parser`는 P1 작업 5 전체, `feat/shared-p1-2.1-model-types`는 2.1이 속한 PR 경계, `chore/p2-28-context`는 P2 컨텍스트 작업 28). 브랜치 이름, 마지막 커밋의 작성자와 날짜를 함께 본다. push하지 않은 다른 사람의 작업은 보이지 않는다.
4. **선행 작업**은 `tasks.md`의 Overview(선머지 범위, 트랙 사이 의존), 작업 본문, Task Dependency Graph로 판단한다. wave는 순서 안내이지 전부가 의존은 아니다. 막는 것으로 보는 것은 선머지 작업, 같은 상위 작업 안에서 앞 wave에 있는 하위 작업, Overview나 본문이 이름을 적은 작업이다. 그 밖에 앞 wave의 미완료 작업은 "확인 필요"로만 알린다.

## 2. 작업 번호가 없을 때
스펙 색인(`README.md`)의 트랙 표를 기준으로 트랙별 목록을 보여 주고 끝낸다. 구현하지 않는다.
- 시작 가능: 선행 작업이 완료됐고 진행 중이 아닌 것. `*` 작업과 결정 대기(Notes의 "막는 작업" 표)에 걸린 작업은 표시해 둔다
- 진행 중: 브랜치 이름, 작성자, 날짜
- 막힘: 기다리는 작업 번호
- 완료는 개수만 적는다

## 3. 작업 번호가 있을 때
1. **작업을 읽는다.** 색인, `tasks.md`의 Overview와 Notes, 그 작업의 본문. 상위 작업 번호(예: `5`)를 받으면 하위 작업을 번호 순서로 진행하고, "PR 경계"가 있으면 경계 하나까지만 한다.
2. **시작해도 되는지 확인한다.**
   - 이미 완료된 작업이면 멈춘다. 다른 사람의 브랜치가 진행 중이면 알리고 계속할지 묻는다.
   - 선행 작업이 끝나지 않았으면 무엇을 기다리는지 알리고 멈춘다.
   - 결정 대기(D-n, G-n)에 걸린 작업이면 색인에 적힌 대로(제안값 또는 요구사항 문구) 구현한다고 알리고 계속한다. 임의로 확정하지 않는다.
   - "사람이 수행"이라고 적힌 작업은 할 일 목록만 보여 주고 멈춘다.
   - 본문에 "주의(… 리뷰)"나 "미정(여기서 정함)"이 있으면 테스트를 쓰기 전에 읽는다. 앞 작업의 리뷰가 넘긴 것이고 스펙만 읽고 추론한 내용이 섞여 있으므로, "주의"는 그 줄이 가리키는 코드로 확인하고 따른다. "미정"은 이 작업에서 정한다("주의" 줄 안에 "…는 미정입니다"로 적힌 것도 같다). 어떻게 정할지 알리고 계속하되, 요구사항을 바꿔야 하는 결정이면 먼저 묻는다.
3. **브랜치를 맞춘다.** 형식은 `feat/<track>-<단계>-<번호>-<slug>`(루트 `CLAUDE.md`). 번호는 PR 단위의 번호다(상위 작업 번호, PR 경계가 있으면 그 경계의 첫 하위 작업 번호). `.claude/`나 `CLAUDE.md`를 고치는 컨텍스트 작업(색인 트랙 표의 "컨텍스트")은 `chore/<단계>-<번호>-<slug>`다(`.claude/rules/context/editing.md`).
   - `main`이면 이름을 제안하고 확인받은 뒤 `origin/main`에서 브랜치를 만든다. 작업 트리에 커밋하지 않은 변경이 있으면 먼저 알린다. 원격이 있으면 `git push -u origin <브랜치>`로 올려 진행 중임을 알린다.
   - `worktree-<이름>` 브랜치면 `git branch -m`으로 이름을 바꾼 뒤 push한다.
   - 이미 이 작업의 브랜치면 그대로 쓴다. 다른 작업의 브랜치면 멈추고 묻는다.
4. **필요한 부분만 읽는다.** `requirements.md`에서 본문 끝 `_Requirements: …_` 번호의 인수 기준만, `design.md`에서 그 작업의 클래스가 나오는 절만(절 제목으로 찾는다).
5. **실패하는 테스트를 먼저 쓴다.** 인수 기준마다 테스트를 하나 이상 대응시키고, 본문이 지정한 예시 테스트를 포함한다. 그 테스트만 실행해 assertion 실패(컴파일 오류가 아님)를 확인한다. 속성 테스트는 그 Property의 `*` 작업에서 쓴다.
6. **구현한다.** 테스트를 고치거나 지워서 통과시키지 않는다. 테스트가 인수 기준을 잘못 옮긴 것이면 멈추고, 어느 기준과 어긋나는지 알린 뒤 고친다. 작업 범위 밖의 파일은 고치지 않는다. 새 의존성이 필요하면 멈추고 묻는다.
7. **마무리한다.** `tasks.md`의 체크박스를 고친다. 설계와 다르게 구현했으면 `design.md`의 그 절을 함께 고친다. 대응시킨 인수 기준과 테스트, 설계와 달라진 점, 제안값으로 구현한 결정 대기 항목, 다음에 할 작업을 보고한다.
   - 본문의 "주의"와 "미정"을 정리한다. 구현하면서 틀린 것이 드러난 "주의"는 그 줄을 고치고 무엇이 달랐는지 보고한다. 정한 "미정"은 그 줄을 `- 결정(<이 작업 번호>): <정한 값과 이유>` 형식으로 바꾸고(예: `- 결정(12.1): 대상 0개일 때 estimatedCostUsd는 0.0000으로 합니다. null이면 CLI가 "단가 없음" 경고를 잘못 내기 때문입니다`) 필요하면 `design.md`에 반영한 뒤 무엇으로 정했는지 보고한다. "주의" 줄 안에 섞여 있던 미정은 그 문장만 떼어 `결정` 줄로 따로 만든다.
   - 이 작업이 정한 동작 때문에 뒤 작업이 스펙만 읽고 구현하면 틀리게 되는 것이 있으면 "뒤 작업에 넘길 것"으로 보고한다(대상 작업 번호, 주의/미정, 한두 문장). 여기서는 `tasks.md`에 쓰지 않는다. `/pr-ready`가 리뷰 결과와 합쳐 수정안을 만든다.

커밋과 PR 생성은 하지 않는다. PR 준비는 `/pr-ready`가 한다.

## 작업 종류별 차이
- `*` 속성 테스트 작업: 구현이 이미 있으므로 테스트만 쓴다. 반례가 나오면 예시 테스트로 고정한 뒤 구현을 고친다.
- Checkpoint 작업: 코드를 쓰지 않는다. 전체 테스트를 돌리고 결과와 질문을 보고한다.
- 코드가 아닌 작업(패키지 이름 변경, 문서, `.claude/`): 5번을 건너뛴다.
